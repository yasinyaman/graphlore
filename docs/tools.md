# graphlore tool reference

All 33 MCP tools, the resources and the prompts. The default `lean` surface
registers 12 of them: `build`, `overview`, `locate`, `search`, `neighbors`,
`subgraph`, `impact`, `node_details`, `fetch`, `communities`, `freshness` and
`project`. The rest need `GRAPHLORE_TOOLSET=full`.

## Tools

See [Which toolset](configuration.md#which-toolset) for choosing a surface.

Building the graph (both write state; `build` is in lean, `add` is not):

| Tool | Purpose |
|---|---|
| `graphlore_build` | Build/update the graph (`update`, `cluster_only`, `code_only`, `mode="deep"`). Returns the build's counts and warnings (`verbose=True` for the full CLI log), says so when the graph landed outside the active project (graphify writes `graphify-out/` inside the folder it reads), and notes vendored/minified files and a `graphify-out/` that git neither ignores nor tracks. When graphify refuses a default build for want of an LLM key (the folder holds docs), it runs again with `code_only` and says so. By default (`GRAPHLORE_ENGINE=auto`) graphlore's native engine builds it when installed (the `engine` extra: definitions with spans, containment, document headings, the imports, calls, bases and type references it resolves from the source, and communities of its own; `update` parses only what changed and `cluster_only` re-detects the communities; see [configuration](configuration.md#the-native-engine)), and graphify only when it is not; graphify and `mode` are deprecated and go in the next release. Either way graphlore writes **`graph.html`** beside graph.json (`no_viz=True` skips it): one offline page that opens on the communities, one bubble each with the strongest links between them, and goes down to a community or a node's 1- or 2-hop neighbourhood, with search, a details panel (file:line, id, connections by relation), filters by relation group (structure, imports, calls, inheritance, references, state, http, documents, other), tests and external packages, and colouring by community or kind; the tests / external packages / vendored filters apply everywhere: to the overview (a community is counted, sized and linked by what they leave, and one left empty is not drawn, the note says how many), and to the panel's lists (community members, a node's edges, impact rows, findings), each saying how many it hid; search still finds a hidden node by name; a document's outline (its page and headings) is drawn whatever the structure filter says, and its `documents` links lead to the code it names. The page also opens any other graph.json ("Open graph.json…" or drop it on the canvas, with its `.graphify_labels.json` for the names), read in the browser; a node's neighbourhood is drawn in columns (what uses it on the left, what it uses on the right, grouped by file), labels never overlap, the address bar keeps the view (`#n=<id>`, `#c=<community>`: a link opens it again, Back and Forward move between views), keys (`/` find, `Esc` back, `F` fit, `1` / `2` depth, `?` the list), buttons that copy `graphlore_explain` / `graphlore_fetch` / `graphlore_impact` / `graphlore_skeleton` calls for the assistant, an **On GitHub ↗** link (GitLab, Bitbucket too) that opens a node's lines in a new tab at the commit the graph was built from (from the repository's `git remote`, only the host and the repository's path kept; a host's page will not sit in a frame, and the page itself still makes no request), and on a phone touch and pinch with the panel as a sheet. For the active project the page also carries what the tools find, from their own answers: **Findings** (`G`, `#f=`) lists the cycles of `graphlore_cycles`, the shared state, surprising links and co-changing files of `graphlore_surprises` and the candidates of `graphlore_unreferenced`, each opening its nodes; **Impact** (`I`, `#i=`) draws what depends on a node within 1–3 hops as `graphlore_impact` walks it, test code counted apart; a node's panel gives its span, qualified name, language, route and coupling pairs, and each edge row when an import runs, its context and its line; on a graphify graph the edges graphlore resolves from the source are drawn dotted and vendored files hidden behind a filter. A page written for another path than the active project has no findings and the reply says why. The same page with no graph in it is graphlore's standalone viewer (`src/graphlore/viewer.html`, and [on GitHub Pages](https://yasinyaman.github.io/graphlore/viewer/)) |
| `graphlore_add` | Add a source by URL (arXiv, tweet); runs the graphify CLI. Deprecated: goes with graphify in the next release |

Project selection:

| Tool | Purpose |
|---|---|
| `graphlore_project` | Show the directory the server reads, or switch it to another one — a second repository, or one just built with `graphlore_build("/abs/path")`. Changes no file; refused under `GRAPHLORE_RESTRICT_PATHS` (always on over HTTP). Also names the server version |

graph.json analysis (read-only, no CLI needed; the payload arrives as `structuredContent`, and `as_json=True` puts it in the text too):

| Tool | Purpose |
|---|---|
| `graphlore_overview` | **Call first** — size, god nodes, communities, surprises, suggested next steps, and the server version |
| `graphlore_god_nodes` | Most connected nodes, ranked inside the [scope](concepts.md#analysis-scope) |
| `graphlore_communities` | Leiden community summaries: the `limit` largest, each with its `size`, its `members` most connected first (`members` of them; the rest counted in `members_left_out`) and its `name` when it has one — set with `graphlore_set_labels` / `graphlore_label_communities`, else the one the build wrote (graphify's, or on a native graph its hub prefixed with the directory most members share) |
| `graphlore_surprises` | Unexpected cross-file connections — listed from the graph's own flags when it has them, otherwise **computed** by scoring cross-file edges (confidence, file-type/directory/community crossing), with resolver noise, anything test code uses (the source under test, shared test fakes) and consumers — a directory or a script nothing depends on, using the package — scored down, as is a pair of directories that many edges already join (an adapter using the application layer is the architecture); an inferred edge into a module the source file imports scores like an extracted one, and one into a module it never imports is dropped; says plainly when nothing is computable rather than printing an empty list On a native graph it also lists **shared state** (`shared_state`): variables, fields and resources written in one file and read or written in another, scored the same way (files that do not import each other, top-level directories, communities), test code left out  `shared_state` rows carry `pairs`: per writer and other toucher, the `call_path` between them (or none: a hidden pair) and whether their files change together; `co_change` lists source files that change together in the git history (last 1000 commits, code-maat's degree) with no edge of the graph between them, and `history` says how much history was read (a shallow clone is named) |
| `graphlore_search` | Node search by name or id; `total` / `truncated` say how many matched beyond `limit` |
| `graphlore_query` | A natural-language question → the part of the graph it is about: the question is searched in the code (the `locate` index; without one, the nodes whose names share its words), up to 3 hits become `seeds`, and the graph is walked out from them, breadth-first 3 hops or with `dfs=True` depth-first 6 hops, until `budget` (2000 tokens) is spent. Takes `scope`; outside lean |
| `graphlore_path` | Shortest path between two nodes: along the edges' own direction (`direction: forward`), else from the second to the first (`backward`), else either way (`undirected`), each step saying which way its edge points; `couples_with` is not walked. Each end may be a bare name, resolved like everywhere else (the reply says which node was used). Takes `scope`; outside lean |
| `graphlore_explain` | Everything the graph knows about a node: what `node_details` gives, plus its connections, tallied by relation and direction (`counts`) and listed up to `limit` (30). Outside lean |
| `graphlore_neighbors` | 1-hop neighbors of a node, production code before tests, most connected first; takes `scope`. Inferred edges and edges graphlore resolved from the source are marked. Past `limit` (200) the result says how many neighbors there are (`total`) and how they split by relation and direction (`counts`) |
| `graphlore_subgraph` | Token-budgeted BFS subgraph around a node — the cheap way to feed the model just the relevant slice (Graphify's embedded server does this too; pairing it with `fetch`/`locate` is what's specific here). Walks production code before tests, so a hub's budget goes to its real callers; takes `scope`, and a truncated result says how many direct neighbors were left out and how many were tests |
| `graphlore_impact` | Reverse-dependency / **blast radius** — what breaks if a node changes (`direction=dependents`/`dependencies`/`both`), filterable by relation (`relations="calls"`, `"code"`, `"imports"`, `"types"`) and by `scope`. Ordered by hop distance, production code before tests; each row carries the recorded reference site and the edge's confidence, and `strict=True` walks only extracted edges. A truncated result says how many rows were dropped and how many were tests, and sets `complete: false`; `beyond_hops` says separately what one more hop would add. Docstring/rationale nodes are left out and counted Reads and writes of shared state (`reads` / `writes`, native graphs) are not walked by default and are counted in `state_nodes_skipped`; `shared_state=True` follows them, from a writer through what it writes to its readers (a `written_by` step), and `relations="state"` names them, together with the `couples_with` edge the native engine writes for a pair that shares state with no call path between them. On a native graph `handles` (route → handler) and `http_calls` (client → route) are walked like calls, so a handler's dependents reach the code that requests it; `relations="http"` keeps only those |
| `graphlore_tests_for` | **Tests for a symbol** — tests that call it directly (with the call line), tests that reach it through one caller (a production function, or a helper/fixture in the test code), and weak matches kept apart (a test file that imports its module, a test named after it). Takes `scope`. Rust tests inside a source file (`#[cfg(test)] mod tests`, `#[test] fn`) count as tests |
| `graphlore_node_details` | Node metadata: type, source file/line, docstring, community. The docstring is framed as repository text. On a native graph, `state` lists what the node reads and writes and `shared_with` the other definitions touching the same state (`affected by this`, `affects this`, `both write it`); for a variable or field, its readers and writers. `http` lists the routes a handler serves and who requests them, the routes a client definition requests, or a route's handlers and callers. `co_change` names the files the node's file changes with most in the git history, and whether the graph joins them |
| `graphlore_skeleton` | def/class **signatures** (decorators kept, bodies stripped) for a file/node/community — the middle layer between the map and full code. A budget cut names the files left out |
| `graphlore_fetch` | **Token-budgeted** source hydration — reads the real code for a node (its enclosing def/class span ± context), the map→code other half of `subgraph`/`locate`. Names past the budget come back in `not_fetched`, missing ones with `did_you_mean`; each entry says `file_changed_since_build`. The first definition is returned whole up to 8,000 tokens (or `budget_tokens`, when that is larger); a longer one — a 3,000-line class — is cut at a line and says so in `cut` (`lines_shown`, `lines_total`, `tokens_total`) and `lines_left_out`, with the budget that returns all of it |
| `graphlore_freshness` | Is the graph stale vs. git HEAD? Returns `recommended_action` (fresh/update/rebuild) + `reason` — lingering phantom nodes / large changes steer to a rebuild; junk files (`.DS_Store`, logs) land in `non_source_changes` and never hold the graph stale |
| `graphlore_diff` | Structural changeset between two git refs (default `HEAD~1..HEAD`) — added/removed/renamed/modified, with cosmetic-only changes separated (file-level, for review/audit) |
| `graphlore_prune` | Drop phantom nodes (and their edges) for deleted/renamed source files — the surgical alternative to a full rebuild (`dry_run=True` to preview) |
| `graphlore_validate` | Lint the graph for dangling/duplicate/self-loop edges and orphan nodes (read-only). Recursion is counted apart, not as an issue. The one result that lists every vendored/minified file (`vendored_files`) |
| `graphlore_duplication_scan` | **Repo-wide** duplication audit in two tiers. **Identical bodies** (exact, no model, always runs): function and method bodies hashed after normalizing whitespace, comments and docstrings, reported as groups — the small helper copied into three modules. **Hidden links** (similarity, on semble or the built-in index): definitions that are similar but structurally distant, each pair with its score and both `file:line`s; `score_kind` says what the score is (embedding cosine, or tf-idf cosine on the built-in BM25-only index), pairs under the floor (0.7 on embeddings, 0.5 on tf-idf) are left out by default (`min_score=0` lists them), and test ↔ source pairs need `include_tests=True`. On the built-in index each seed is anchored on its own definition's chunk. Outside lean |
| `graphlore_cycles` | Circular dependencies **by kind**. Import cycles between modules come first, each import read back from the source and classified: **runtime** cycles (a loop of module-level imports — the ones that fail at start-up), then **deferred** (closes through an import inside a function) and **type-only** (closes under `if TYPE_CHECKING:`). Then call cycles, then the rest — each with one concrete loop. `kind="imports"` asks for one kind; recursion is listed apart |
| `graphlore_layers` | **Layer rules** — give `{"layer prefix": ["prefixes it may import"]}` (inline, or a JSON file in the repository) and get the import edges that break them, grouped by layer with `file:line` and when the import runs (module-level / `TYPE_CHECKING` / inside a function). An import the source contradicts — `import yaml` linked to a first-party `yaml.py` — is not checked and is listed apart. The same check as an AST-based dependency test, read from the graph. Takes `scope` |
| `graphlore_unreferenced` | **Dead-code candidates** — functions, methods and classes with no incoming graph reference, not registered by a decorator (routes, click/typer commands, validators, fixtures), and not mentioned anywhere else in the repository's text. Another definition of the same name and its uses are not mentions, so the unused one of two same-named classes is still found. Each with `file:line` and a mention count; a lower bound on what is alive, not proof of death |
| `graphlore_same_names` | Classes and top-level functions that **share a name across modules** (within one language; closures are not compared), each copy with how many modules import it and whether its own file uses it — the model-free companion of the duplication scan's identical-bodies tier. A name with more than 25 definitions lists the first 25 and counts them all (`definitions_total`) |
| `graphlore_package_apis` | **Symbol-level external API surface** — which names each external package is actually used for (`fastapi: Depends, APIRouter`), with qualified paths (`numpy.linalg.norm`) for version-diff audits; a lower bound (dynamic/star/getattr use is invisible). Python via stdlib ast and JS/TS, Go, Java from use sites; Kotlin, Scala, C#, Rust, Swift, C/C++, Ruby and PHP from their imports (`[treesitter]`). The project's own packages are left out per language: Python and Go modules, the packages and namespaces its JVM/.NET/PHP files declare, its crates, gems, Swift targets and header directories (`first_party_skipped`). Source files in a language with no reader are counted in `not_read`. With `package=`, each symbol's file list is cut at `limit` (shorter still when the package has hundreds of symbols; `symbol_file_counts`, `files_left_out`, `qualified_paths_left_out`, `truncated`). Takes `scope` (`-tests` for what production code uses) |
| `graphlore_routes` | **Framework route → handler table** — which URL patterns hit which code, joined back to graph nodes (`GET /items/{id} -> read_item (app.py:5)`). Python: FastAPI/Flask/Sanic/Quart/Litestar/Django. JS/TS: Express-style (labelled express/fastify/koa/restify/polka by the import; also `router.route('/x').get(h)`, and in a file that imports no framework a receiver named like a router or passed in as a parameter, when some file of the project imports one, or takes it by a relative path in the framework's own repository: `require('../../')` in express's examples), NestJS. Go: gin/echo/chi/gorilla/net-http (Go 1.22 `"GET /x"`, gin 3-arg `Handle`, chi nesting). Java: Spring, JAX-RS. Kotlin: Spring, Ktor. C#: ASP.NET Core controllers and minimal APIs (`MapGet`, `MapGroup`). Rust: axum, actix-web. Ruby: Rails `routes.draw` (`resources`, `namespace`, `scope`), Sinatra. PHP: Laravel `Route::` chains, Symfony `#[Route]`. On a native graph (schema 5) the rows are the graph's route nodes (`source: "graph"`): the full path with prefixes from other files (FastAPI `include_router`, Express `app.use`, NestJS `setGlobalPrefix`, gin groups passed to a function, axum `nest`, Laravel's `routes/api.php` prefix), the handler, and `called_by` / `callers`, the code whose requests reach the route. A lower bound: dynamic registration and prefixes set in configuration are invisible, and so, on a graphify graph, are prefixes applied in another file. Python via stdlib ast; the rest need `[treesitter]`. Takes `scope`; test code is left out by default (`+tests` for a test's throwaway server). Source files in a language with no route reader are counted in `not_read` |

Semantic naming (uses the **host model via MCP sampling** — no API key):

| Tool | Purpose |
|---|---|
| `graphlore_sampling_status` | Capability test: reports whether the client supports host-LLM sampling and which method will be used |
| `graphlore_label_communities` | Give Leiden communities human-readable names. `method="auto"` (sampling → placeholder), `"sampling"` or `"placeholder"`; without sampling, name them yourself with `graphlore_set_labels` |
| `graphlore_set_labels` | Persist **assistant-provided** community names (sampling-free fallback) to `.graphify_labels.json` and into `graph.html` (graphlore's own is written again; an older graphify one is patched) |

Search bridge (code search joined to graph structure; semble when installed, else the built-in index — see [the search bridge](concepts.md#search-bridge-built-in-index-or-semble)):

| Tool | Purpose |
|---|---|
| `graphlore_locate` | NL query → enclosing graph node → token-budgeted subgraph, **plus hidden links**: semantically-similar code that is structurally disconnected (duplication / missing-abstraction candidates) — the `semantic_cousins` with `linked: false`, listed first and counted in `hidden_link_count`. A question often has two homes, so two lists follow the seed: `calls_into` (what the seed calls in other files, most specific first — the implementation behind a thin tool) and `also_matched` (the other top hits by the definition they fall in; hits on a file's docstring-and-imports header are counted, not listed). `backend` says what answered: `name` (`builtin` / `semble` / `custom`) and, for the built-in index, `mode` (`hybrid` or `bm25`), `tiers`, the files and chunks indexed, what was skipped, and `dense_unavailable` when the embedding tier could not load |

## Typical workflow

1. `graphlore_locate("where do we retry failed requests?")` — one-call orientation
   (or `graphlore_overview()` → `graphlore_subgraph("SomeNode")` to start from the map)
2. `graphlore_fetch(["Client._send_single_request"])` — hydrate exactly the code you zeroed in on
3. `graphlore_impact("Response")` — blast radius of a change; with `GRAPHLORE_TOOLSET=full`,
   `graphlore_cycles()` / `graphlore_routes()` for targeted analysis
   (reviewing a codebase: `graphlore_validate` → `graphlore_cycles` → `graphlore_layers` →
   `graphlore_unreferenced` → `graphlore_same_names`; the `review` prompt scripts it)
4. `graphlore_query("how does the auth flow work?")` — a free-form question, answered with the part of the graph it is about (`full`)
5. After code changes: `graphlore_freshness()` → `graphlore_build(update=True)`
   (plus `graphlore_prune()` after deletes/renames)

## Resources

- `graphlore://report` — the graph's report: `graphlore_overview` and `graphlore_surprises`, made from graph.json (the `GRAPH_REPORT.md` graphify wrote, beside a graphify graph)
- `graphlore://graph` — graph.json (raw)
- `graphlore://community/{id}` — per-community wiki (members + internal/boundary edges)

## Prompts

Reusable templates that orchestrate the tools for the assistant:

- `onboard` — orient to the codebase (overview → communities → subgraphs → surprises → summary)
- `trace_bug(symptom)` — find likely root-cause locations through the graph
- `explain_flow(flow)` — end-to-end walkthrough of a named flow with file:line refs
- `review` — review structure: cycles, layering, dead and duplicated code (needs `GRAPHLORE_TOOLSET=full`)

Each prompt is rendered for the active toolset: a step whose tool is switched off
is left out, or replaced by one that is on (`trace_bug` uses `graphlore_impact`
where `graphlore_path` is off).

## What a result carries

- **Tool annotations** (`read_only_hint`, `destructive_hint`, titles) tell the model which tools are safe to call freely vs. which mutate state.
- **Server instructions** describe the recommended flow (locate/overview → targeted subgraph/fetch → build update).
- **`as_json` output** on every analysis tool — including error and no-match paths — returns structured data the model can chain on instead of re-parsing prose.
- **MCP structured results.** Over the protocol every analysis tool's payload also arrives as `structuredContent` (the same object `as_json=True` prints), whichever text form was asked for, and failures — node not found, missing graph, a failed CLI call — set `isError: true`. An empty but valid answer (no search hits) is not an error. No `outputSchema` is published: payload shapes differ per path. `GRAPHLORE_STRUCTURED=0` falls back to plain text results.
- **Token budgeting on source, not just structure** — budgeted subgraph rendering is Graphify's own (its embedded server does the same); graphlore extends the discipline to *code*: `graphlore_fetch` and `graphlore_skeleton` hydrate real spans under a cap, so escalating map → signatures → source never blows the context.
- **A cut says how to get the rest** — a result that reports `truncated` carries a count of what a limit or budget dropped and a one-line `hint` naming the argument to raise or the filter to add.
- **Unambiguous names** — when several nodes share a bare label (five `.auth_flow()`s across auth classes), rendered output qualifies them with the span-recovered FQN (`DigestAuth.auth_flow()`) or a `file:line` suffix, so an arrow always names exactly one symbol.
- **Repository text is framed as data.** `graphlore_fetch`, `graphlore_skeleton`, `graphlore_node_details` and `graphlore_explain` (the docstring) and `graphlore_add`'s CLI output put the code and text they quote between `=== repo text <nonce> ===` markers, with a per-call random nonce redrawn if it occurs in the text, so a comment in the repository cannot close the frame and pose as graphlore. JSON replies say `content_trust: "untrusted_repo_text"` and name the `untrusted_fields`. A docstring that says "ignore previous instructions" is still a docstring.
- **Host-LLM sampling** (`graphlore_label_communities`) lets the server borrow the client's model via MCP `sampling/createMessage`, so semantic naming works with no server-side API key — with a capability test (`graphlore_sampling_status`); without sampling, `graphlore_set_labels` takes names the assistant writes itself.
