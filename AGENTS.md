# AGENTS.md

Guidance for AI coding agents working in this repository. This file is the single source: Codex, Cursor and Copilot's agent features read it directly, and `.claude/CLAUDE.md` and `GEMINI.md` import it. `.github/copilot-instructions.md` is a condensed copy for the Copilot features that read only that file; when a rule changes here, update it there too.

## What this is

graphlore is a Python MCP server that makes a code knowledge graph (`graphify-out/graph.json`, built by its own native engine) navigable and joins it to real source spans. Building the graph is graphlore's native engine's job (`engine/`, the `graphlore-engine` wheel, a dependency of graphlore). The external `graphify` CLI (PyPI package `graphifyy`) built it before 0.9.0; a graph it wrote is still read. What lives in `src/graphlore/` is graph analysis plus the span engine (stdlib `ast` for Python, tree-sitter for everything else).

`engine/` is graphlore's own extractor, written in Rust: a separate distribution, `graphlore-engine` (import name `graphlore_engine`), built with maturin + PyO3, with its tree-sitter grammars compiled in. It is the only extractor (`GRAPHLORE_ENGINE` takes `auto` or `native`, both the engine; `graphify` is refused), installed from prebuilt PyPI wheels (`.github/workflows/engine-wheels.yml`): for 14 languages it writes files, definitions with their `start..end` spans, properties and constants, containment (`contains` / `method` / `defines` / `case_of`), Markdown/RST headings (Sphinx `.txt` sources included) and a `documents` edge from a heading to the one definition a name of code under it means, the imports, calls, bases and type references it resolves from the source, shared state (variables, fields, constants and resources such as environment variables, files, tables and events, with the `reads` / `writes` of the definitions that touch them), and communities of its own (Leiden on edges weighted by kind, confidence and directory); `update=True` parses only the files that changed. graphify went in 0.9.0; what reads graphify's graphs goes in the release after (the three releases are in `docs/native-engine.md`'s roadmap). graphlore itself stays pure Python: the Claude Code plugin builds it from source on the user's machine, so Rust must never enter its own build (`pyproject.toml` excludes `engine/` from the sdist; the engine comes as a prebuilt wheel).

It is built on the **MCP Python SDK v2** (`mcp>=2.1,<3.0`): `mcp.server.mcpserver.MCPServer`, not v1's `FastMCP`, and `ToolAnnotations` with snake_case fields (`read_only_hint`, `destructive_hint`).

CI (`.github/workflows/ci.yml`) runs `ruff check .`, `mypy` and pytest with coverage on Python 3.10–3.12, so code must stay 3.10-compatible; its `engine` job runs the cargo checks, builds the wheel and runs the suite with the engine installed. The default branch is `master`. Unlike the Python sources, `engine/` is `cargo fmt`-formatted (`engine/rustfmt.toml`) and CI checks it.

**Don't run `ruff format .` across the repo.** CI doesn't check formatting and 8 of the 11 Python files (including `server.py` and `tests/test_tools.py`) are not ruff-formatted, so it rewrites them wholesale. Match the surrounding style by hand unless a reformat is the task.

The multi-language tests skip themselves when the `[treesitter]` extra is absent. When it is installed, `tree-sitter-language-pack` downloads grammars from GitHub releases on first use (cached under `~/.cache/tree-sitter-language-pack/`); if that download fails, those tests **fail** rather than skip (`assert None is True`, `KeyError`, empty route lists). Those symptoms look the same as a real regression in the tree-sitter extractors, so check before dismissing them:

```bash
python -c "from tree_sitter_language_pack import get_language; get_language('javascript')"
```

A `LanguageNotFoundError: Download error` means the grammars are unavailable and the failures are environmental. If it succeeds, the failures are real.

## Architecture

`src/graphlore/` is layered bottom → top; each module imports only from earlier entries in this list (plus one sideways import: `routes.py` uses `_strip_quotes` from `apis.py`):

- `agents_md.py` — the usage guide for agents that read a project file (AGENTS.md, GEMINI.md, Copilot's instructions) rather than the server's instructions or prompts: `render(tools)` names only the toolset's tools, between `<!-- graphlore:begin -->` / `<!-- graphlore:end -->`; `merge` replaces only that part of a file. Imports nothing from graphlore.
- `clients.py` — the MCP clients `graphlore setup` knows (`CLIENTS`: project and user config files, JSON key or Codex's TOML, the file its agent reads, its own add command), `render` (the block to paste) and `write` (merge, keeping every other server, after a `.graphlore.bak`; a file it cannot parse is refused). Imports nothing from graphlore. A client format changes only with its page re-read (`docs/clients.md` cites them).
- `cli.py` — the `graphlore` console script: no arguments runs `server.main()` (the plugin, `mcp.json` and `server.json` start it so; never add a required argument), `setup <client>`, `clients`, `agents-md`, `review`. It imports `server` only to run it or to name the toolset's tools, and `change_review` only for `review`. `import graphlore` loads none of them (`__init__.py`'s exports load on first use): `graphlore hook` runs on every tool call of an agent.
- `hooks.py` — `graphlore hook pre|post` and `python -m graphlore.hooks`, Claude Code's and Codex's command hooks (one file shape): the call's JSON on stdin, `hookSpecificOutput.additionalContext` on stdout or nothing, exit 0 always. `pre` (Grep / Glob, or a `Bash` command that is a search, `rg` / `grep` / `git grep`, for one identifier the graph defines) names where; `post` (a git command that moves HEAD past `built_at_commit`, an edit of a source file, Codex's `apply_patch` read for the files it names) says the graph is behind, once per state. It runs on every tool call: it imports only `config` and the standard library (never `server`; `_SOURCE_SUFFIXES` is `server._SOURCE_EXTS` copied, a test holds them equal), reads graph.json once per build into a name index under `config.cache_root()`, gives git one second, passes on only plain paths, and is silent on any error and under `GRAPHLORE_HOOKS=0`. `clients.write_hooks` merges the two into `.claude/settings.json` or `.codex/hooks.json` (`graphlore setup claude-code|codex --with-hooks`, matchers per client in `HOOK_MATCHERS`); the plugin ships them in `hooks/hooks.json`, whose matchers cover both clients' tool names.
- `oauth.py` — OAuth for the HTTP transport, graphlore as a resource server: `settings()` reads `GRAPHLORE_AUTH_ISSUER` / `AUTH_RESOURCE_URL` / `AUTH_SCOPES`, `JwtVerifier` is the SDK's `TokenVerifier` (the provider's JWKS by RFC 8414 / OpenID discovery, asymmetric algorithms only, `iss` / `aud` / `exp` required), `apply(mcp, conf)` sets the SDK's auth settings and verifier before `main()` builds the HTTP app (the SDK then answers 401 / 403 and serves the RFC 9728 metadata). pyjwt is the `remote` extra, imported only when configured; the key fetch is network egress (refused offline). Imports only `config`.
- `config.py` — `env(name)` reads `GRAPHLORE_<name>`, falling back to the legacy `GRAPHIFY_<name>`; holds `PROJECT_DIR` and `OUT_DIR_NAME`.
- `engine.py` — the native engine from the Python side (`GRAPHLORE_ENGINE`, read per call: `refusal()` says why a build cannot run — `graphify`, an unknown value, the engine missing — or nothing), `build()` runs `python -m graphlore_engine build` (`--incremental` for `update=True`) and `cluster()` runs `... cluster` (for `cluster_only=True`) in a child process (a grammar crash cannot take the server down), `render_report()` is the build reply, `file_spans()` is the span fallback `spans.py` uses when Python tree-sitter is missing. It never imports `graphlore_engine` at module import.
- `graph.py` — loads `graph.json` (cached by path + mtime), schema-tolerant node/edge accessors, adjacency, BFS, SCC cycles, hop distances, surprise scoring, shared state (`_STATE_RELATIONS`, `_COUPLING_RELATIONS`, `_shared_state`, `_engine_pairs`, `_with_written_by`), HTTP (`_HTTP_RELATIONS`, `_is_route_node`, `_native_routes`), token estimation. No MCP dependency.
- `algorithms.py` — graph algorithms over plain adjacency maps, with no graph.json knowledge: `certain_route` (fewest inferred steps, then fewest steps: `graphlore_path`), `pagerank` and `betweenness` (Brandes, exact or from hash-sampled sources: `graphlore_god_nodes`' `rank=`), `dominators` / `dominated_counts` (Cooper–Harvey–Kennedy: `graphlore_impact`'s `chokepoints`) and `cut_structure` (Tarjan's bridges and cut vertices with what each cuts off: `graphlore_bridges`). Deterministic: ties follow the order of the lists handed in, samples a hash of the id. Imports nothing from graphlore. `tests/test_tools.py` checks each on small graphs; they were checked against networkx on 300 random graphs.
- `history.py` — files that change together, from one local `git log` (the last 1000 non-merge commits, renames followed, commits of more than 30 files skipped; code-maat's degree), cached on `(PROJECT_DIR, HEAD)`. A shallow clone or a history under 10 commits is reported (`History.note()`), never read as "nothing changes together". No network.
- `spans.py` — the span engine: per-file `(region_start, end_line, def_line, qualname)` spans, `_node_for_location` (semantic chunk → enclosing graph node), `_structurally_equal` (the cosmetic-vs-structural diff behind freshness/diff/watch), and the shared per-file pipeline `_cached_file_analysis`.
- `scope.py` — the analysis scope shared by the analysis tools: parses the `scope` string, detects vendored/minified files, and hands back a cached `ScopeView` of the nodes and edges it keeps.
- `apis.py`, `routes.py` — per-file extractors (external package API usage; framework route → handler) built on the `spans.py` pipeline.
- `imports.py` — import statements read from the importing file's source (Python via `ast`, JS/TS via tree-sitter): `ImportChecker.kind` says when the import behind a file-level import edge runs (module-level, deferred, type-checking) and rejects an edge the source contradicts (`import yaml` linked to a first-party `yaml.py`).
- `scip.py` — a SCIP index read with the standard library (`_fields` decodes the protobuf by `scip.proto`'s field numbers, the typed ranges 8 / 9 before the packed one): `load()` gives an `Index` (`defs` symbol → (file, line), `refs` occurrences, `tools`, `errors`) of the files `GRAPHLORE_SCIP` names (`auto`: `index.scip` at the root or in the output directory; never a path outside the project), cached on their stats; `bare_name` reads a symbol's last descriptor (scip-python's `` `pkg.mod`/__init__: `` is `mod`); a use whose source text at its range is not that name is left out (`Index.mismatched`: an indexer's slip on re-exported names, an alias), and `Index.def_of` matches a symbol by its descriptors too, the module ending the definition's (`click.utils` of the installed copy is the project's `src.click.utils`). scip-go and scip-dotnet: a package named by its import path is its last segment (before a major version: `chi/v5` is `chi`) and an import writes the whole path; a `` `.ctor` `` is named as its type, an attribute without `Attribute`; a first line's byte-order mark is no character; a symbol defined more than once (partials, namesakes scip-dotnet gives one symbol) is every definition (`Index.more_defs`, `defs_of`), an edge to any of them is confirmed and a use adds none; a definition's own signature naming what holds it adds nothing, and an edge to a constructor where the index names its type is not contradicted (`ctor_of`). `benchmarks/conformance.py --scip` reads the cases in precise mode (runs the indexer on each case's project). `resolve._precise` uses it after `_from_source` (so on native graphs too): confirmed / added / contradicted edges (`scip`, `resolved_by: "scip"`), cached on the identity of the lists and the index, the owner of a use from the nodes' `region_start` / `end_line` where they have them. Imports only `config`; reads a local file, nothing else.
- `resolve.py` — edges the graph lacks and the source proves: `_resolved(nodes, edges)` returns the graph's edges plus calls and imports made through a module object (`mod.func()`; Python, plus JS/TS default and dynamic imports), marked `resolved_by: "graphlore"`, as one cached list.
- `review.py` — the review analyses with no MCP dependency: unreferenced code, same-named symbols, identical bodies, layer rules.
- `viz.py` — `graph.html`, graphlore's own offline view of the graph: `page_data` compacts graph.json (nodes and edges as index arrays, relations grouped by `relation_group` from `graph.py`'s sets, communities counted), `render` puts it into `viewer.html` (canvas and plain JavaScript, no library, a CSP that allows no request), `write` skips a graph over `MAX_NODES`. `source_of_remote` turns a git remote into `{host, web, commit, prefix}` (github.com, gitlab.com, bitbucket.org; only the host and the repository's path, never a user name or token) for the panel's "On GitHub ↗" link; server.py's `_viz_source` reads the remote and the built commit with local git only. The page opens on the communities and goes down to one community or one node's neighbourhood (at most 400 nodes drawn). Repository text is embedded with `<`, `>`, `&` escaped and shown with `textContent` / `fillText` only, never as markup. Written after every build, `cluster_only`, `graphlore_set_labels` and `graphlore_prune` (graphify's own graph.html is only patched, `viz.is_ours`). `viewer.html` with no data embedded is a viewer of its own, and every page has an "Open graph.json" button: it reads a graph.json (and a `.graphify_labels.json`) in the browser through `compact()`, the JavaScript twin of `page_data` between its `// compact:begin` / `// compact:end` markers, with `RELATION_GROUPS` the twin of `relation_group`. Change the two together: `test_the_viewer_reads_a_raw_graph_as_python_does` runs the block under node against `page_data` and checks the table against `graph.py`'s sets (and `IMPACT_NEVER` / `IMPACT_FROM_STATE` against `graphlore_impact`'s skip sets, `viz.impact_walk`). What graph.json alone cannot give is `page_data`'s `analysis`, which `compact()` never makes: `server._viz_analysis` runs `graphlore_cycles`, `graphlore_surprises` and `graphlore_unreferenced` for the active project's graph only, maps their display labels back to node positions (`_NodeFinder`), adds the vendored files and, on a graph the engine did not resolve, `_resolved`'s added edges, and caches it on (path, mtime); a failing tool is a line of `notes`, never a missing page. The page's impact view is `impactOf` between `// impact:begin` / `// impact:end` (with `withResolved`): `test_graph_html_shows_what_graphlore_s_tools_find` runs it under node on every node against `graphlore_impact`, so a change to how impact walks changes both. `.github/workflows/pages.yml` publishes it to GitHub Pages (`viewer/`, and `viewer/demo.html` with the polyglot fixture). Imports only `graph`.
- `embed.py` — the optional dense tier of the built-in search: loads a model2vec static model (`[embed]` extra) behind `config.export_offline_env()`, and `VectorStore` keeps chunk vectors by text hash (in memory, and on disk under `GRAPHLORE_CACHE_DIR`, never in the project). Imports only `config`.
- `search.py` — graphlore's own code search, the `graphlore_locate` / duplication-scan backend (`auto`; semble only with `GRAPHLORE_SEMANTIC_BACKEND=semble`): one chunk per span-engine definition (a container holds only its own lines), identifier-aware BM25F over name / path / body plus a graph overlay (docstring, call-neighbour names), the dense tier fused by weighted reciprocal rank, a path prior and per-file decay. `index_for_project()` keeps one `CodeIndex` per (`PROJECT_DIR`, model) and refreshes it per call by file (mtime, size). The hot loops sit behind `_Kernel` (`tokenize`, `bm25f`); the native engine's `SearchKernel` (`engine/src/search.rs`, `KERNEL_ABI`) replaces `_PyKernel` when installed, and `tests/fixtures/search_golden.json` is the contract both meet bit for bit.
- `server.py` — the whole MCP surface in one ~8,000-line module: the `mcp` instance, 33 tools, resources, prompts, toolset trimming, the opt-in watcher, HTTP bearer auth and `main()`.
- `change_review.py` — `graphlore review`, on top of the stack: it imports `server` and joins the tools' own functions (`graphlore_diff`, the impact walk `_hop_records` over `_nav_view`, `graphlore_tests_for`, `_tiered_import_cycles`, `graphlore_layers`) into one report of a commit range: each changed line (`git diff -U0`) given to the innermost definition around it, the dependents of all of them in one walk, the tests, and the import cycles and layer violations written on a changed line (`introduced`). It builds the graph at the head commit when it is not there (native engine), refuses otherwise (exit 2), and `--fail-on` gates exit 1. Markdown quotes every repository name as a code span (`_code`); deterministic, offline, no model.

`graphlore_build` runs the native engine in a child process (`_build_native` / `_cluster_native`, through `engine.build` / `engine.cluster`, an argv list with no shell), after `engine.refusal` says it can (an `ERROR` with `code: engine` otherwise). `query`, `path` and `explain` are graph.json tools: they no longer run graphify, and community naming is sampling or `graphlore_set_labels` only (`method="cli"` is refused). **graph.json analysis** tools read the graph directly and must keep working with no optional extras installed.

Optional dependencies (`semble`, `model2vec`/`numpy` for `[embed]`, `tree-sitter`, `tiktoken`, `watchdog`, `uvicorn`, `graphlore_engine`) are imported lazily inside functions and degrade to a fallback or an install hint; nothing may raise `ImportError` at module import.

## Conventions that span files

- **Read `config.PROJECT_DIR` by attribute**, never `from .config import PROJECT_DIR`: tests repoint it with `monkeypatch.setattr(server.config, "PROJECT_DIR", tmp_path)`, and `graphlore_project` reassigns it at runtime. For the same reason nothing may cache a value derived from it without keying on it. Under `GRAPHLORE_PROJECT_FROM_CLIENT` (a plugin started in its own directory) `config.project_pending` is True until the client's roots or `graphlore_project` name the project, and `_tool`'s wrapper answers every tool but `_PROJECT_FREE_TOOLS` with `code: project_unknown` meanwhile (a direct call of the function skips that check).
- **Settings go through `config.env("NAME")`** so the legacy `GRAPHIFY_*` fallback applies. Several are captured once at import as `server.py` module constants (`TOOLSET`, `TRANSPORT`, `RESTRICT_PATHS`, `API_KEY`, …) and tests patch the attribute; others (`SEMANTIC_BACKEND`, `WATCH`, `ALLOWED_HOSTS`, `TOKENIZER`, `OFFLINE` via `config.offline()`, `STRUCTURED`, `ENGINE` via `engine.requested()`) are read at call time.
- **Network egress:** every path that can reach the network checks `config.offline()` (refuse, or degrade to a local-only variant and say so); the "What reaches the network, and when" table in `docs/configuration.md` lists them and must stay in step. A new optional dependency that downloads on first use gets a row there and a gate. The native engine never reaches the network (its grammars are compiled in); keep it that way.
- **Repository text is framed:** a tool whose text reply quotes source, docstrings or CLI output derived from them wraps it in `_frame_repo_text(...)` and puts `content_trust: _CONTENT_TRUST` and `untrusted_fields` in the payload. graphlore's own notes go outside the frame; errors are never framed.
- **Tool shape:** a plain sync function returning `str` (the SDK runs sync tools in a threadpool), registered with `@_tool(annotations=...)`, never `@mcp.tool`. `_load_graph()` returns either the graph dict or an error *string*; check `isinstance(graph, str)` and return `_err(msg, as_json)`. Success returns `_fmt(payload, as_json, text)`. With `as_json=True` every path, including errors and no-match, must return parseable JSON.
- **MCP results:** `_tool` registers a wrapper (no outputSchema) and leaves the module attribute as the plain function, so direct calls and tests get the string. `_fmt` / `_err` record their payload in a per-call `ContextVar`; when the tool returns exactly that string, the payload becomes the result's `structuredContent`. `_err` sets `isError`, and so does `_fmt(..., is_error=True)` for a failure that still has a payload. An empty but valid answer (no search hits) is `_fmt`, not `_err`. `_err(msg, as_json, **extra)` keeps `error` a string and adds sibling keys (`code`, `did_you_mean`). A reply built without `_fmt`/`_err` has no structuredContent and is an error only when it starts with `ERROR`. `GRAPHLORE_STRUCTURED=0` turns all of this off.
- **The one async tool** is `graphlore_label_communities` (`async def`, takes `ctx: Context` and a keyword-only `Resolve` parameter that must have no default; see the comment on its signature). An async body runs on the event loop, so any blocking work added there goes through `anyio.to_thread.run_sync`. Tests drive it over an in-memory session (`_run_in_memory`), not by calling it directly.
- **Schema tolerance:** graphify's `graph.json` shape varies. For id, label, file, line, edge endpoints and relation use the accessors: `_nodes_edges`, `_node_id`, `_node_label`, `_node_file`, `_node_line`, `_node_type` (`type`, else graphify 0.9's `file_type`), `_edge_ends`, `_edge_rel`. Fields without an accessor are read with `.get()` and a fallback, never `[]`; community is `n.get("community", n.get("cluster"))`. Relation names are compared against the sets in `graph.py` (`_IMPORT_RELATIONS`, `_CALL_RELATIONS`, `_CONTAINMENT_RELATIONS`, …), never against a literal: graphify adds relations between releases (`defines`, `case_of`, `dispatches_to` in 0.9), and `benchmarks/polyglot.py` reports any that no set names.
- **Ambiguous labels are qualified by `_display_labels(nodes)`** (`DigestAuth.auth_flow()` or a `file:line` suffix). Use it for nodes named in edge, neighbor and list rows. A row that prints its own `file:line` column uses `labels.name(id)` instead, which never adds a location suffix. The resolved subject of a call (`center`, `node`, `seed` in the payload) keeps its bare `_node_label`.
- **Import edges go through `ImportChecker`.** graphify resolves imports by name, so a tool that lifts import edges to file level (`_file_import_edges`, `_module_import_adjacency`) passes `ImportChecker().kind` — one instance per call — and reports `checker.rejected` rather than silently trusting or dropping edges. It reads Python with `ast` and JS/TS with tree-sitter (following an import through a re-exporting `index.ts` to the file graphify linked it to), treats compile-time languages (Go, Java, Kotlin, Scala, C#, Rust, Swift, C, C++, Objective-C) and PHP as module-level, and returns `unclassified` (kept, counted as module-level) for anything else. A new source reader, here or in `resolve.py`, covers every language the project already parses or says per language why there is nothing to read — the `apis.py` extractors are the model.
- **Identity-keyed caches:** `_adjacency`, `_directed_adjacency`, `_edge_set`, `_exact_node_index`, `_name_index`, `_edge_flags`, `_nodes_by_file`, `_display_labels`, `_test_node_ids`, `_importers_by_file` and `_edge_index` (the HTTP and state indexes of `graphlore_node_details`) are keyed on `id()` of the nodes/edges list that `_load_graph` hands back. Pass those lists through unchanged; a copied or filtered list misses the cache on every call. The sanctioned derived lists are `_resolved(...)`'s extended edge list and a `ScopeView`'s: `_scoped` builds it once per graph and returns the same objects afterwards (and returns the original lists when the scope leaves nothing out).
- **Implicit coupling is stated per pair.** `_shared_state` gives each writer × other toucher pair its `call_path` (calls, dispatch and HTTP, 6 hops, on the resolved edges) and `co_change`. On a native graph of schema 6 the engine has worked the pairs out (`engine/src/coupling.rs`): the state node's `coupling.listed` is the answer `_shared_state` takes (`_engine_pairs`), and it looks for a path itself only for a pair the node does not list, so the two must keep the same rules (`test_native_implicit_coupling_matches_the_python_reading`). A hidden pair's `couples_with` edge is in `_COUPLING_RELATIONS` and so in `_NON_DEPENDENCY_RELATIONS`: derived from `reads` / `writes`, it is never a reference, a cycle or a surprise of its own, and `graphlore_impact` walks it only when state is asked for. Test code is `_in_test_code(n)` there (a test path or the engine's `test`); a hidden pair (no call path) is what scores. `graphlore_surprises`' `co_change` and `graphlore_node_details`' `co_change` read `history.history()`; a reply that uses the history carries `history` (`commits`, `shallow`, `skipped_bulk`, `note`), and code that reads co-change goes through `History.coupled` / `partners` / `coupled_pairs`, not its counts.
- **Name resolution:** every tool that takes a node name (impact, subgraph, neighbors, tests_for, node_details, fetch, skeleton) resolves it with `_pick_node`, reports `_matched(key, picked)` (several matches, or a substring fallback, which is never silent) and answers a miss with `_not_found(nodes, key, as_json)`, which adds `code: "not_found"` and `did_you_mean`. Don't call `_resolve_node` from a tool.
- **A cut says what it left out:** a budget or limit that drops rows reports `truncated` plus a count or the names left out (`not_fetched`, `files_left_out`, `total`, `counts`, `beyond_hops`) and a one-line `hint` on how to get the rest (`_cut_hint(payload, "...")`). Never cut silently. The same goes for a language nobody reads: `graphlore_package_apis` and `graphlore_routes` count the source files they have no extractor for in `not_read` (`_not_read(files)`).
- **Spans are generic, and checked on real code.** `spans.py` walks any tree-sitter grammar: a node is a definition when its type carries a hint word and it names itself (a `name` field, a C/C++ declarator chain, or an identifier child in a grammar without name fields). A type merely written in a signature is not a definition. Several spans can start on one line, so a node's own span is `_span_of_definition(file, line, bare name)`, not the innermost one. Whether a node is test code is `_is_test_node(n)` — a test path, or a Rust `#[cfg(test)]` / `#[test]` region of a source file (a module or a function under the attribute) — not `_is_test_path` of its file. After changing the rules, run `benchmarks/polyglot.py` (below): the unit tests hold a few lines per language, the audit holds whole repositories.
- **Node-centric tools** (impact, subgraph, neighbors, tests_for) resolve their node as above; they read `_nav_view(nodes, edges, scope, as_json)`, which is the resolved edge list under a scope that leaves nothing out by default; they order rows production-before-tests; and an empty result carries `_EMPTY_NOTE`. `_resolved` edges are never written back: `graphlore_prune` and `graphlore_validate`'s lint read the raw graph.
- **Analysis scope:** a tool that ranks or audits the graph takes `scope: str = ""` and goes through `_scope_view(nodes, edges, scope, as_json)`. Compute on `view.nodes` / `view.edges`, label with `_display_labels(all_nodes)`, put `view.payload()` under `"scope"` and wrap the text in `_with_note(text, view)` so what was left out is always stated. The default leaves out vendored/minified files and external nodes.
- **Path confinement:** the per-file analyzers and source hydration (spans, APIs, routes, `fetch`, `skeleton`, `prune`) resolve every path from the graph, a semantic chunk or a file/node argument through `spans._resolve_in_project`, usually via `_cached_file_analysis` or `_read_source_lines`. Don't open such paths directly. Three things sit outside it on purpose: `graphlore_build`'s `path` is unconfined by default (absolute and sibling-repo paths are a documented use) and is guarded only by the opt-in `_path_escapes_project` (`RESTRICT_PATHS`, forced on for HTTP transports); `graphlore_project` accepts any directory and is refused outright under `RESTRICT_PATHS`; and freshness/diff/watch read git-reported paths relative to `config.PROJECT_DIR`. `review._count_mentions` walks the project directory itself (like `_route_candidate_files`) and never follows a link out of it.
- **`server.py` re-exports private helpers** from the lower modules (`# noqa: F401`) because tests reach them as `server._x`. A new helper that tests use that way needs adding to the re-export block.
- **stdout is the protocol on stdio transport**; diagnostics (boot banner, warnings, watcher logs) go to stderr.
- **Naming:** `graphlore_*` tools and `GRAPHLORE_*` variables belong to this project. `graphify-out/`, `.graphify_labels.json` and the `graphify` binary are artifacts of the wrapped CLI and keep their names.

## When adding or changing a tool

A tool is registered with `@_tool(annotations=ToolAnnotations(...))` in `server.py`; keep it read-only unless it genuinely mutates state and set the matching hint. The change also touches:

- the tool list in the `server.py` module docstring, and `LEAN_TOOLS` / `LOCATE_TOOLS` if it belongs in a trimmed surface. `lean` is the default surface, so a tool outside it is invisible to most users unless they set `GRAPHLORE_TOOLSET=full` (the plugin does)
- `_instructions(active)` and the prompts (`_render_prompt` steps) if the tool belongs in the recommended flow: they name a tool only when it is registered. A reply that points to another tool wraps the pointer in `_tool_hint(name, text)`
- `test_tool_and_prompt_registration` in `tests/test_tools.py`, which asserts the exact tool count (33)
- the tool tables in `docs/tools.md`, the README's table of the 12 `lean` tools if the tool is in that set, and the "33" / "12" counts in both
- its docstring: a description of at most 900 characters (what it is for, what the reply carries) and an `Args:` entry for every parameter, which `_describe_parameters` moves onto the input schema as each parameter's `description` (`_doc_args`); parameters stay plain types (a mapping is a JSON string with `_JSON_OBJECT_ARG` and `_json_object`, an optional number a sentinel default, never `X | None`). `test_every_parameter_has_a_description_and_descriptions_stay_short` and `test_input_schemas_use_what_every_function_calling_api_takes` hold the limits (Claude Code cuts a description at 4,096 characters, Codex compacts a schema over 5,000 bytes, Gemini CLI caps a tool name at 63)
- `skills/graphlore-explore/SKILL.md` (shipped to users by every plugin; `.claude/skills/graphlore-explore` is a link to it for this repository's own sessions)
- `CHANGELOG.md` under `[Unreleased]` — every behavior change gets an entry there (Keep a Changelog format)

The version is duplicated in `pyproject.toml`, `server.__version__`, `.claude-plugin/plugin.json`, `plugin.json`, `gemini-extension.json` and `server.json` (twice there; tests compare all but the first), and recorded in `uv.lock`; run `uv lock` after a bump. The release steps, including the PyPI publish workflow, are under "Releasing" in `CONTRIBUTING.md`.

## Plugins

The repository root is itself a plugin, in three formats, and its own marketplace:

- **Claude Code:** `.claude-plugin/plugin.json` and `.claude-plugin/marketplace.json` (`"source": "./"`). Codex and Copilot CLI read that marketplace file too. Its hooks are `hooks/hooks.json`, the default place of both Claude Code and Codex (which sets `CLAUDE_PLUGIN_ROOT` too); the manifest has no `hooks` key, which Claude Code would merge with that file and run each hook twice. They run `python3 -m graphlore.hooks` with `PYTHONPATH=${CLAUDE_PLUGIN_ROOT}/src`, so the hook needs nothing installed but a Python.
- **Agent Plugins 1.0** (Codex, Copilot CLI; Cursor by its documentation): `plugin.json` at the root (a closed schema: `$schema`, `name`, `version`, `description`, `author`, `homepage`, `repository`, `license`, `keywords`, `extensions` only), `mcp.json` (the spec's format, `type: stdio`, started in the plugin root, so `uvx --from "graphlore[…] @ ."`) and `skills/`, a fixed location. The spec is `agentplugins/agent-plugins-spec` on GitHub.
- **Gemini CLI:** `gemini-extension.json` (`${extensionPath}`, `${workspacePath}`) with `.gemini-extension/GRAPHLORE.md` as its context file, which is `agents_md.render` of the full toolset. Without `contextFileName` Gemini would load the root `GEMINI.md`, this repository's own guide, into every user's session.

Consequences:

- `skills/` is what every plugin ships to users. Anything added there is installed for everyone.
- Every manifest's MCP server runs `uvx --from "graphlore[treesitter,embed] @ <its own copy>" graphlore`, i.e. it builds this package from the installed copy of the repo. Renaming the console script, the package or those extras breaks the plugins. `test_plugin_manifests_stay_in_sync` holds the versions, the extras, the skill path and the Gemini context file together.
- An Agent Plugins client names no project: `mcp.json` sets `GRAPHLORE_PROJECT_FROM_CLIENT=1` and never `GRAPHLORE_PROJECT_DIR` (see the conventions above).
- Users stay on a manifest's `version` until it changes, so a fix reaches plugin users only with a version bump.
- Check manifest changes with `claude plugin validate --strict .`; it passes clean.
- Claude Code's project instructions live in `.claude/CLAUDE.md`, not at the root. A `CLAUDE.md` at a plugin root is not loaded as plugin context and makes the validator warn, so don't add one there.

## The native engine (`engine/`)

- `src/generic.rs` is the port of `spans.py`'s definition rule (`_spans_treesitter` and its helpers), in the same order. Keep the two in step: `tests/test_engine.py` asserts that `graphlore_engine.file_spans` equals `spans._spans_treesitter` (and, for Python, `spans._spans_python`) on a snippet per language. A rule change in `spans.py` gets the same change in `generic.rs`.
- A language is a `Lang` variant, a row in `SPECS` (`src/lang/mod.rs`: name, extensions, grammar crate) and a module in `src/lang/` implementing `LanguageModule`, whose methods all default to the generic rule; a module overrides only what its grammar does differently: definitions (`kind_of`, `region_start`, `end_line`, `test_regions`, `refine`, `bound_functions`, `emits_node`, `extra_def` for properties / constants), and the facts resolution needs (`imports_of`, `heritage_of` / `heritage_owner`, `package_of`, `exports_of`, `object_of`, `refs_of`, `is_field`, `builtins`). Each new language gets a sample in `tests/grammars_load.rs`, goldens in `tests/spans_golden.rs` and a small project in `tests/edges_golden.rs`, and a resolver for its module paths in `src/resolve/modules.rs`.
- `src/refs.rs` reads the uses (calls, constructions, bases, types, decorators, attribute reads, values passed) and typed names (parameters, fields, `x = Foo()`) with field-name rules shared by the grammars; `src/resolve/` turns them into edges. Resolution order matters and is documented at the top of `resolve/mod.rs`: scope lookups are `EXTRACTED`, a project-wide guess by name alone is `INFERRED` and needs evidence (a unique candidate; for an unknown receiver, a distinctive method name in a file the caller imports or its directory). Never add a lookup that guesses before the scopes are exhausted, and an external module's contents name nothing.
- Locals in resolution (`resolve_path`): a typed local resolves through its type; a local the walk cannot type still hides every outer name of its own (only a distinctive method name is tried on it, `INFERRED`), except a bare call beside a typed local (`baseUrl(…)` beside `String baseUrl`), a local assigned from the outer thing of its own name (`let agent = agent();`) and an assignment hint (`Local::assigned`: `service = make()` where assigning declares nothing), which keep the outer meaning. PHP `$x` keeps its `$` in paths and is only ever a local. A use inside a field first assigned in a method belongs to the method (`refs::homes`), not to the class the field hangs off. A name bound to an import (`const x = require('m')`, `require('m').y`) is not a state definition. An `Extension` definition never answers a name lookup (`top_in`), and neither does an anonymous class (`Def::anonymous`: the method around constructs the type it implements, the class has it as its base). A closure's parameters are names of the closure only (`refs::bind_closure_params` renames their uses to `name@byte`); never record them as locals of the function. A closure no definition holds (`test('…', () => { … })`, an RSpec `it … do … end`, a module wrapped in a function) is a definition of its own (`Def::block`, `refs::add_blocks`): no node (`assemble`), no name (`index`), its parent the block around it, the home of the uses and locals inside it (their edges leave from the file), and the parent of a definition written in it, which it sees as a function sees its nested ones (`resolve_name_any`); an RSpec `let` keeps its own `scope_lines` and is never re-parented. A block is never a span: `file_spans` leaves it out (`tests/test_engine.py` holds a snippet with a callback at file level). A Rust macro outside any definition is a block too, and `refs::macro_refs` returns the locals its arguments bind (a closure's typed parameters, a `let` in its body) with the uses, `name@byte` moved to the file's bytes. A closure called where it is written as a declaration's value (`var X = (function () { function X() {} return X })()`) gives the definition of the declared name written in it `Def::returned_out`: `index` registers it in the scope of the declaration too (it stays the block's child, so it still sees the block's other definitions), and the declaration is no local. A declaration whose value is a function that is a definition of its name (`const f: T = () => …`) is no local either. `assigned_member` is a function assigned to a function as its member (`X.extract = function`), in its file. RSpec `shared_examples` and the places that include them are `FileFacts::shared_examples` / `example_includes`: `shared_example_let` answers a bare name in the examples with the `let` in scope where they are included, only when every including place gives the same one. An extension function or method (`Def::receiver`) is a member to its callers (`extension_method`: `EXTRACTED` on a matching receiver type, `INFERRED` on a single visible candidate). The receiver's type counts with its bases (`extension_for`), a field or property of a type the project does not define with the type it declares (`extension_on_member`; `refs::predefined` keeps C# `string`), a local with the type its value constructs (`local_built_type`), and never by a `CSHARP_CORE_METHODS` name on a receiver that is no project type. A C# 14 `extension(T x) { … }` block parses as a constructor named `extension` with local functions; the engine keeps it as a scope only (`LanguageModule::scope_only`: `Def::block`, kind `Other`, no node, name or span, its members named and owned as the class's, `BodyExtensions.HasFiles`), whose parameter is a local its members see (`refs.rs` reads a block's signature as a callable's): `CSharp::receiver_of` gives them the block's parameter type, and `fit` takes no receiver off their parameters (`in_extension_block`). A C# partial type is all the definitions of its fully qualified name with as many type parameters (`partials`): `members`, `field_of` and `bases` read them all. A construction also calls the constructor the type declares, picked among overloads by argument count (`RefFact::args` / `Def::params`) and left out when that does not decide. Ruby: a bare name that is no local is a call (a hash's value too: only a `pair`'s key names nothing, `Ruby::refs_of`), a module is every file that opens it (`reopened_member`, `qual_key`; `reopened_base_member` for what another opening mixes in or extends, and `Ruby::heritage_of` reads the block of `X = Struct.new(…) do … end` too), a top-level method of a file the caller does not require is not in scope, and a name called without parentheses is followed through what it returns. An RSpec `let(:x) { … }` / `subject` is an extra callable definition (`Ruby::extra_def`) with `Def::scope_lines`, the `describe` / `context` block it is written in: only the scoped lookup at the top of `resolve_name_any` finds it (the innermost block around the use), never `top_in`, `by_qual` or a guess by name; its result is the block's last expression (`Def::returns`), and the call that declares it is no use. `FileFacts::spec_includes` (`config.include M`) answers, in a test file only, a bare name nothing else does (`spec_helper_member`). What a call gives is `return_type`: the declared result, else what the body's `return`s and expression body construct when they agree (`Def::returns`, `INFERRED`; a closure's `return` is not the function's). A local keeps the whole chain it is assigned (`value_type` drops only a chain that starts at something unnameable), and inside its own initializer its name is the outer one (`own_initializer`). A Kotlin lambda with a receiver is a `ReceiverScope` (`x.apply { … }`, `with(x)`, a parameter typed `T.() -> R` via `Def::lambda_receiver`); `RefFact::recv` names the innermost one around a use, and `receiver_member` is asked after the locals and before the class around — never while typing a path written elsewhere (`type_of_path` clears it). An untyped local or parameter is an unknown receiver (`unknown_receiver`); in Ruby and Swift only for a name no other type answers to (`sole_holder`: no property, no `FileFacts::attrs` entry, not a core-library name), and never on a local of an external type, which only an extension can answer. Overloads (`Family::overloads`: Jvm, C#, Swift, C/C++) are chosen after resolution by `pick_overload` / `fit`: `Def::plist` (names, written types, defaults, varargs) against `RefFact::args` / `hints` (literal kind, typed path, label); `fit` returns `None` only when the facts rule a candidate out, and what they do not say counts for nothing — never make an unknown a mismatch. Constructors go through the same `fit`, with a Kotlin class's primary constructor (the class's own `plist`) as a candidate that names no definition. A result typed by a self-bound type parameter (`Def::self_params`) is the type the method was called on; a local's `given` type (one type argument or class literal of its value's call) is its type only through `given_result`'s checks. When several overloads fit alike `pick_overload` returns them all and each edge is `INFERRED`: never name the first as if it were known. A local with no type is typed by `structural_type` (the one type answering every non-core member used on it, two names at least); a collection's element type is `Local::elem` / `ParamFact::elem` / `Def::elem`, a path ending in `refs::ELEMENT` (`[]`) names an element (`elem_of`), and loop variables, iteration-lambda parameters and `xs[0]` are locals with such a path. The path walk (`resolve_path_inner`) carries `many`: what it holds is a collection of itself, after a name, field or call declared as one when something of collections follows (`is_collection_step`), after a `KEEPING_METHODS` name, or after `refs::MANY` (`[+]`, which `refs::mapped` ends a mapping's path with: `xs.map { it.owner }` is `xs`, `[]`, `owner`, `[+]`); an `ELEMENT_ACCESSORS` name or `[]` leaves it, `UNWRAPPERS` are skipped on the element just taken, and a path that ends `many` names nothing unless `elem_of` asked (`want_many`). A collection method as the last name of a call is the library's: never an edge to the element type. A path with `[]` / `[+]` that does not resolve is retried as an unnamed receiver (`()` and what follows). It also carries `sealed`: `t` is what a closed wrapper holds (`Def::sealed` / `Local::sealed`, read by `refs::sealed_type` from the `SEALED` names; `Def::wraps` is what a wrapped result or field holds, and `return_type` reads it first). `refs::OPENED` (`[?]`, written by `path_of` / `value_type` after `await` and Rust `?`) and an `UNWRAPPERS` name open it, `SEALED_KEEPING` names keep it, anything else on a closed wrapper names nothing; `resolve_path_inner` takes `[?]` out of the path and keeps where it was (`opened_after`). `Result` and `Task` are wrappers only in Rust and C# (`refs::language_wrapper`): another project may define its own. Maps: `refs::map_value` gives a map type's values as its element and `keyed` (on `Def`, `Local`, `ParamFact`) says it is a map; the walk carries `keyed` and `indexed` (after a `PAIRING_METHODS` name) beside `many`. Three markers end a path to one of a collection: `[]` (`refs::ELEMENT`: an index or key, a map's value), `[*]` (`ITERATED`: what an iteration gives, nothing of a map or of pairs) and `[v]` (`VALUE`: the second of a pair taken apart, a map's value or the element beside an index); `elem_of_as` takes the marker. `KEY_LOOKUPS` give a map's value, `MAP_VIEWS` change what it is (`keys` gives the key type, `Def::key` / `Local::key` / `ParamFact::key` from `refs::map_key`, carried as the walk's `keys`). A fourth marker, `[k]` (`refs::KEY`), is the first of a pair taken apart: a map's key, a list's element, nothing beside an index; `[+=]` (`MANY_KEYED`) ends an `associateWith` mapping. `partition` taken apart keeps the collection for `[#0]` / `[#1]` (`partitioned`), `refs::zipped` gives each name of a pair over `zip` its own side, `refs::fold_value` is what a fold starts from (its result and accumulator), and `Def::returned_parts` (`note_parts`) names what a tuple part is when its type does not (`local_function`). The library-method rule (a collection's or wrapper's method as the last name of a call names nothing) holds for a call being linked, not for a local's value being typed (`linking_call`, `typing_value`). Generics: a class-like `Def::type_params` holds its own type parameters, and `targs` (on `Def` for a field's type and a callable's result, on `Local`) the type arguments written; the walk carries `Binds` (the generic type and what each parameter stands for, each with the file and scope it is written in), set from a local's or field's `targs` and passed through a result written with the class's own parameter (`binds_for`), and read by `bound_type` / `bound_field` only for a member of that very class and never for a method's own type parameter. A `BoundArg` carries the argument's element when it is a collection (`Def::targ_elems` / `Local::targ_elems`: `bound_param` answers whether the type is that element); a member a base declares takes the bindings the base is written with (`Def::base_targs`, `inherited_binds`, three levels); a local typed by its value takes the bindings its value's walk ends with (`end_binds`, `local_value_binds`, cached like `local_types`). The walk's `nest` counts lists of lists beyond `many` (`NESTING_METHODS`, `GROUPING_METHODS` add one, an element marker or `FLATTENING_METHODS` take one off); `ASSOCIATING_METHODS` make a map of the elements, `REDUCING_METHODS` give one. It must stay deterministic and stable: nodes are visited by a hash of their id, never a global shuffle; a build starts from the previous graph's communities (`Previous::read`, the graph.json it replaces) and settles until a pass returns its own start. A pass is Leiden over the graph, then graphify's size and cohesion splits; Leiden starts from the groups the communities were split out of (`Walk::top`, from `graph.communities.parents`: the lists of two or more communities split out of one group, `Previous::parents`), a split from the communities (`Walk::before`), and a pass is the same only when both are (`Part::tops`). Started from the split communities, Leiden merges the splits again and the splits come out a little different each time: settling never ends (`GRAPHLORE_SETTLE_TRACE=1` prints what each pass did). It writes `coupling` on the state node (`pairs`, `hidden`, `listed`, at most `PAIRS_LISTED`) and a `couples_with` edge per hidden pair (at most `EDGES_PER_STATE` per state node, from the definition that sees the state to its writer, `via` the state), which `community::detect` skips, as it skips the override `dispatches_to` edges (both repeat edges it already weighs: check that communities stay where they were when adding a derived relation). It is the port of `graph._shared_state`'s pairing: a rule changed in one changes in the other. The path needs dispatch in the graph: `Project::dispatch_pairs` (`resolve/mod.rs`) links a base's method to each method written for it (`dispatches_to`, `context: override`; the nearest declaring base, no constructors; where the family has overloads the parameter count, the written types when either type has several such methods of the name, and Swift's labels always (`same_signature`); Rust by the `impl Trait for Type` a method stands under, Go never), with goldens in `tests/dispatch_golden.rs`.
- `src/http/` reads routes and requests per language (`python.rs`, `ecma.rs`, `jvm.rs` for Java and Kotlin, `csharp.rs`, `go.rs`, `rust.rs`, `ruby.rs`, `php.rs`), after `src/graphlore/routes.py`'s rules and gates (a framework is read only in a file that imports it, by name or, in the framework's own repository, by a relative path to the directory whose `package.json` names it): `RouteFact`s, routers with a prefix (`RouterFact`, `scope` for one bound in a definition), mounts (`MountFact`: a router named, a module required, a function's router parameter `Mounted::Param`), global or per-file prefixes (`GlobalPrefix`) and requests (`CallFact`). A route's router path can be `SELF_ROUTER` (the router the enclosing function builds) or `[PARAM_ROUTER, "N"]` (its `N`th parameter). `src/resolve/http.rs` composes the full paths across files (`compose`, memoized, depth 8), turns them into route nodes (unique ids: two paths that slug alike get a counter) with `handles` edges, and links requests to routes (`link_calls`): only production code (requests in test code are counted), segment by segment, the most literal match first, then the route nearest the request; `EXTRACTED` only for a single candidate with a known method and no value-against-parameter segment. A handler path is taken only from an `EXTRACTED` resolution; `Handler::Class` finds a controller by name (`articles#index`, `UserController@store`). Keep `routes.py` and these readers in step: `route_parity.py`-style checks (every `routes.py` row of the audit repositories is a route of the native graph) and `tests/http_golden.rs` hold them.
- The reader and the resolver are shared by the 14 languages, so **a rule that is one language's asks which language it is reading** (`parse::current()`, `Family`, `FileFacts::lang`): a name table consulted without asking has made `Box` a wrapper in Java and dropped the `$` of a TypeScript name. `benchmarks/neutrality.py` checks it by differential testing: every name of every `const NAME: &[&str]` table of `refs.rs`, `resolve/mod.rs`, `state.rs` and the language modules, plus name shapes and other languages' keywords, as a method on a typed receiver, a method called on `self`, a bare function and a generic type the project defines itself, in each language, against the same project with a neutral name. A new table or a new spelling rule is run through it (`--tables NAME`), and a row it adds to `benchmarks/results-neutrality.json` is a leak unless the language reserves the name. A wrapper's name is the project's own type in a file that sees the project define it: the reader cannot know, so `lib::reread_shadowed` reads those files a second time with the names in `parse::shadowed` (it is the same from the cache: what a file defines and imports does not depend on it). `self` / `super` are plain names where the language has no such word and the scope has one (`plain_word` in `resolve_path_inner`).
- `src/walk.rs` honours `.gitignore` for what git does not track, and reads what it does: `tracked_but_ignored` asks `git ls-files` (git is the engine's one external program; no git or no repository adds nothing) for the tracked files the walk left out, minus hidden paths, `SKIP_DIRS`, the output directory and the root's `.graphloreignore` / `.graphifyignore`. A manifest found that way counts (`packages/zod/package.json` under `**/package.json`). A Go module's `vendor/` (`modules.txt` in it, a `go.mod` beside it: `walk::go_vendor_dir`) is left out, tracked or not, unless `BuildOptions::read_vendor` (`--vendor`, `GRAPHLORE_VENDOR=1`); the report names it (`vendored_skipped`, `vendored_skipped_count`) and its imports are external modules. `tests/tracked.rs` holds both. A workspace (`walk::workspace_repos`: a root that is no repository with checkouts one or two levels down, or `.graphlore-workspace.json`; `config.workspace_repos` is its Python twin, keep the two in step) asks each repository for its own files and commit (`graph.repos`); `Project::repo` is each file's repository, and an import with candidates in several (`py_resolve`, `ns_target`, `rs_crates_in`, `js_resolve`'s packages, `go_resolve`'s modules) takes the importer's, and `Project::best` keeps the asking file's repository (`asking`, set by `resolve_path_inner` and `scope_of`) of candidates in several (a Ruby constant, a PHP class); `resolve/http.rs` links a URL to a host the workspace file maps only to that repository's routes, and route ids lead with the repository. `tests/workspace.rs` holds it; on the Python side `_graph_repos` / `_workspace` / `_repo_dir` give the git layer (`_age_at`, `_drift_at`, `_repo_freshness`, `_diff_records`) its repository, never `config.PROJECT_DIR` alone (`docs/workspace.md`).
- Where a language's compiler says what a name is bound to, it is the judge: `benchmarks/oracle_typescript.py` compares the engine's edges with the `.symbols` baselines of the TypeScript compiler's test suite, `benchmarks/oracle_scala.py` with the Scala 3 compiler's SemanticDB expect files, `oracle_kotlin.py` with the Kotlin Analysis API's resolver tests and `oracle_swift.py` with the Swift index tests; `oracle_go.py`, `oracle_rust.py` and `oracle_csharp.py` ask `go/types`, rust-analyzer and Roslyn about whole repositories (precision: an edge whose site the compiler has an answer for goes to that declaration; the "missed" list is a list to read, not a recall). Run it after a change to the shared resolver, read the `wrong` rows, and turn a real one into a conformance case first. `benchmarks/verify_cases.py` checks that the checklist's own programs are ones their languages accept.
- A rule is read out of the language's own tools before it is looked for on a repository (`docs/rule-sources.md`; `benchmarks/rule_sources.py` fetches the binder, the version table and the specification of each language): the grammar's `node-types.json` for a position a name can be written at, the compiler's binder and the specification for which declaration it means. Whether the reader looks at a place at all is measured, not noticed: `benchmarks/positions.py` lists every place a type name is written (the node that holds it and the field) with the share the engine read; a reader change runs it with `--baseline`, a new unread place is read (case, then code) or goes into its `DECIDED` with the reason. A rule that depends on the language's version says so (`since` / `until` on its case; `found_by(...)` in `conformance.py` records how the cases after it were found, `source=` where a rule was read). `engine/src/versions.rs` reads the version a project states from its manifests (`versions::read`, `versions::of_file`: the nearest manifest at or above the file, a stated version before one a framework only implies) and `lib.rs` writes it to `graph.language_versions`; no rule reads it yet, and one that will asks it the way a one-language rule asks the language. A new manifest kind is a name in `walk::MANIFESTS` (or `MANIFEST_SUFFIXES`), an arm of `versions::of_manifest` and a line of `tests/versions.rs`. A rule of a language is a case before it is code: `benchmarks/conformance.py` holds one small project per name-resolution rule (the edge the rule says is there, the edge that must not be), and `benchmarks/results-conformance.json` their state. A resolution change runs it with `--baseline` (a case it breaks exits 1), a rule found missing on a repository is added there as a case first, and `docs/resolution-rules.md` is regenerated from it. A failing case is an open defect, not a failing test: the goldens in `engine/tests/` hold what works.
- An edge only graphify has is a gap only when it is right: for a Go, Rust or C# repository `benchmarks/verify_graphify.py` asks the compiler about each of graphify's edges and gives the share of the confirmed ones the native graph has; read that number, and its list of confirmed edges the native graph lacks, before chasing a row of `compare_engines.py`. The confirmed edges are a floor: `--baseline benchmarks/results-verify-graphify.json` fails a build that lacks more of them, per repository and kind, than the file says (`--update` after closing some). What the resolver leaves out is measured, not guessed: `BuildOptions::unresolved` (`build --unresolved PATH`) writes each call with no edge whose name is the one callable of that name in the project, with the reason (`Project::explain_unresolved`), and `benchmarks/unresolved.py` counts them. Run it before and after a resolution change (`--json`, `--baseline`) and read samples of the reason the change is for; asking for the rows must never change graph.json (`tests/unresolved.rs`). A row carries `library_like` (why it is most likely a library's name: a core name — the `*_CORE_METHODS` tables, Rust's and C++'s only for this —, a library's receiver, a capital head that names nothing of the project, `self` under an outside base, a test-code definition for a production call) or null; mark a new kind of noise there, not in the script. A member of a type that implements a library type (`implements_library_type`: an outside base not in `MARKER_BASES`, never Ruby) is marked on an untyped receiver (`UNTYPED_RECEIVER_REASONS`), not when the receiver's type is known. A path that reaches something written with a library's type (`library_typed`, `is_outside_local`) is the library's unless the one definition is an extension; a bare call names no method where `Family::implicit_this` is false; an RSpec `let` is a candidate only for a bare name; a member of a name a type declares with no `def` (`self.attrs`: a Ruby `Struct` member, `attr_accessor`, `def_delegators`) is marked whatever the receiver.
- `src/search.rs` is the port of `search.py`'s kernel (`_PyKernel.tokenize`, `_word_terms`, `_stem`, `_WORD` / `_PART`, `bm25f`): the same terms and bit-identical scores, in Python's order of operations, its digits `search_digits.rs` (Python's `str.isdigit`). A change to one is a change to the other, with a case in `tests/fixtures/search_golden.json` (held by `tests/search_kernel.rs` and `test_builtin_search_kernel_matches_the_golden_contract`); bump `KERNEL_ABI` in both only when the interface changes. `definition_spans` (`parse::defs_for_source`) is `file_spans` without the rest of the facts (C++ reads them all: `Def::unspanned` needs the locals); `tests/spans_golden.rs` checks the two equal on every golden.
- The resolver's edges stay `graph::links::TypedEdge`s to the write (a JSON object per edge cost about ten times the edge: 4 GB on kubernetes): `Links` is the assembler's link objects, the resolver's typed edges, then the documents' and coupling's objects, in graph.json's order; coupling, communities and the report read them through `Link` (`LinkSource`, also implemented for a `[Value]`), and `GraphOut` writes them with the same keys in the same order. `build` never makes them JSON; `build_graph` does at the end, for its caller. The facts are written to the cache and let go right after `docs::link::edges`, before coupling. A change here keeps graph.json byte-identical on the audit repositories; the report's `memory_mb` (Linux) gives the memory after each phase.
- Resolution is incremental (`src/resolve/trace.rs`, `reuse.rs`): what each file's resolution reads is recorded in a frame, and an update takes the file's edges from `cache/graphlore-resolved.bin` when nothing it read changed (its print, the prints of the files it read and of the keys it asked); another set of paths, other manifests or another engine resolves every file. So every read of another file's data goes through what records it: `Project`'s per-file tables are `Traced` (`self.files[g]`, `self.def`, `top`, `children`, `scopes`, `def_ids`, `hubs`), its maps by file `FileKeyed` (`locals`, `shadows`), its project-wide indexes `Named` / `NamedSet` (a lookup records the key, a found one or not; a type's `fields` are one, their print naming each local by `decl::local_id`). A read of a file is of all of it (`trace::part::FULL`) or of its declarations only (`part::DECL`): `def()`, `top`, `children`, `scopes`, `def_ids`, `hubs`, `files.decl(g)` (`DeclView`: definitions, path, language, package, imports, exports and the other declaration fields, and `decl_refs`, the references written in declarations: bases, decorators, a declared result) and a local of a class or namespace (`local_at`, `local_index`, `shadow_list`, by `decl::holds_declarations`) read the declarations, whose print is `decl.rs`'s (everything they hand out, with each position as its rank among the file's declaration positions: resolution compares a file's positions only with one another, so a line added to a body changes no rank); `self.files[g]` and everything else of a body (its references and locals, `used_on`) read all of it. A new accessor reads the declarations only when `decl.rs` prints all it hands out, and a position it hands out is compared with positions of its own file only; anything else reads the whole file. `GRAPHLORE_REUSE_VERIFY=1` resolves every file and says which of those whose resolution would be reused came out otherwise (run it on the audit repositories after touching any of this), `GRAPHLORE_REUSE_WHY=1` why each file is not reused, `GRAPHLORE_TRACE_FILE=path` which sites read a file and how much of it; `.raw()` reads without recording and is for building the indexes and the passes after the main loop only. A scan of every file (`.iter()`) makes the file depend on everything (`Frame::all`): a lookup that needs one is a table built in `index_scans` and asked by key instead. A new index is a `Named` with its prints in `key_prints`. The caches of resolution are emptied at each file (`forget`) and keep the mark of where a value was worked out (`Trace::epoch` / `valid`), except `bases_memo`, kept across files with the flattened frame of what working it out read (`open_kept` / `close_kept`): a new cache follows one of the two patterns, never a value kept across files without its frame. `tests/incremental.rs` and `benchmarks/incremental_check.py` (seeded edits, update against a full build, byte for byte) hold it; run the second after touching any of this. `GRAPHLORE_RESOLVE_ORDER=reverse|shuffle:SEED` resolves the files in another order (the graph must not change), `GRAPHLORE_TRACE_STATS=1` prints what the frames hold. The main loop's body is `resolve_file`, run by workers (`resolve_workers`: one per `FILES_PER_WORKER` files to resolve, or `GRAPHLORE_RESOLVE_THREADS`; one while a measurement counts reads per site), each with a `Project` of its own: per-file state stays in the worker, what a file gives goes back to its place (`FileRun`, `trace::Flat`: nothing shared by `Rc`), and what the passes after the loop read of the workers' work is joined into the main project (`used`). Nothing a file's resolution gives may depend on which files the same worker resolved before it; the 45 audit repositories build byte for byte the same graph with four workers and with one.
- `src/cache.rs` is the facts cache behind `update=True` (`BuildOptions.incremental`): bincode, keyed on engine version, schema, build options and `FORMAT` (raise it when what an `Entry` holds changes), read with a size limit so a damaged file cannot ask for memory. An `Entry` is the stamp, the facts, the names the file was read with as the project's own types (`reread_shadowed` reads a file again only when those differ, either way) and the hash of its facts; an entry is taken out by its file's read, never copied, and the cache is not written again when nothing was parsed, read again or removed (`cache_kept`), nor the resolution cache when every file's resolution was reused (`resolve_cache_kept`). A new field on `FileFacts` and its parts must deserialize (`Deserialize`; a `&'static str` goes through the `Context`-style alias and `cache::static_str`).
- Read a node's child by field name with `parse::Fields::by_field` and its kind with `parse::Kinds::kind_str`, never tree-sitter's `child_by_field_name` / `kind`: those look the name up by string at every call, which was half the time spent reading files; the two keep the answer per language and thread and give the same.
- Grammar crates must depend only on `tree-sitter-language` (not on the core crate), or they pin a second core. Kotlin is `tree-sitter-kotlin-sg` (the fwcd grammar `spans.py`'s rules assume) because `tree-sitter-kotlin` pins an old core.
- graph.json keeps graphify's shape and conventions so every reader works unchanged: node-link top level, path-slug ids (`core/src/lib.rs` + `Fixed.acquire` → `core_src_lib_fixed_acquire`), labels `name()` / `.name()` / bare, a file hub per file, `source_location` whose leading number is the definition line. Additions are extra keys (`kind`, `qualname`, `language`, `region_start`, `end_line`, `test`, edges' `runs`, externals' `ecosystem`, top-level `graph.engine` / `graph.resolution` / `graph.communities`, nodes' `kind: variable | property | constant`, resource nodes' `type: resource` / `resource` / `key`, state nodes' `coupling`, `couples_with` edges' `via` / `effect`); `community` / `community_name` are graphify's own keys; never write `type` or `line` on code nodes, which the accessors prefer.
- The engine's version lives only in `engine/Cargo.toml` and is independent of graphlore's. `SCHEMA_VERSION` (`src/lib.rs`) changes when graph.json changes in a way readers must know about; `engine.SUPPORTED_SCHEMAS` lists the ones this graphlore reads, and `test_engine_version_pins_stay_in_sync` checks the two.
- graphlore's `dependencies` pin `graphlore-engine` to its minor (`>=0.5.79,<0.6`; the `engine` extra is kept empty so `graphlore[engine]` still installs): a release of the engine that graphlore needs is published first (an `engine-vX.Y.Z` tag), then the pin and `uv lock` follow.

## Reading a language's rules: the sweep

A language's name-binding rules are read out of its specification and its compiler's binder section by section, to the end, not found one at a time on repositories. The work is split by model on purpose:

- **A smaller model extracts** (Claude Code: `.claude/workflows/rule-sweep.js`, Sonnet; any agent can follow the same steps). One reader per group of sections returns, for every rule, the section, the source's own words, and whether a case of `benchmarks/conformance.py` already holds it, a new case (a small project, the edges it expects and the edges of the wrong meaning) or why the engine does not follow it; a section with no rule of name binding says so. A second reader per group looks for what the first missed, until a round finds nothing. The readers write no file of the repository and never touch the engine.
- **The strongest model verifies and fixes.** It runs `benchmarks/sweep_check.py` on the result: each new case given to the compiler (`verify_cases.py`), asked of the type checker where one answers (`verify_cases.py --binding`: an expectation the compiler contradicts is wrong, whatever the engine does) and built by the engine. It reads every "not followed" reason and every case before merging, writes the ones that pass under `found_by("sweep")` and the rows into `benchmarks/rule_inventory.py`, then fixes the engine for the broken ones the usual way (case, code, golden, every baseline).
- **Done** when `python benchmarks/rule_inventory.py --lang L --sections` reads no section as `not read`. The sections are `SECTIONS` there (`--sweep-groups` gives the workflow its groups), and `NO_RULE` holds those with no rule of name binding, each with its reason. `docs/rule-sources.md` ("Phase 2b: the sweep") has the method and each language's numbers.

## Tests

Everything is in `tests/test_tools.py`, except the native engine's end-to-end tests, which are in `tests/test_engine.py` and skip themselves when `graphlore_engine` is not installed; its Rust tests are in `engine/tests/`. An autouse fixture clears `GRAPHLORE_ENGINE` for every test. `tests/conftest.py` pins `server.TOOLSET = "full"` for every test: `server.main()` trims the shared `server.mcp` for real, and the default is `lean`. Tests call tool functions directly (`server.graphlore_overview(as_json=True)`) and parse the result. The `project` fixture gives a temp project with the 5-node fixture graph; `empty_project` has no graph. Tests needing a specific shape write their own `graphify-out/graph.json` into `tmp_path` and repoint `PROJECT_DIR`. Protocol-level behavior (schemas, sampling) uses the SDK's in-memory `Client(server.mcp)` driven by `asyncio.run`; there is no pytest-asyncio. Freshness/diff tests build a real git repo in `tmp_path`.
