# AGENTS.md

Guidance for AI coding agents working in this repository. This file and [`engine/AGENTS.md`](engine/AGENTS.md) (the native engine's rules) are the single source: Codex (`engine/AGENTS.md` under `engine/`), Cursor and Copilot's agent features read them directly, and `.claude/CLAUDE.md` and `GEMINI.md` import both. Keep this file under Codex's 32 KiB limit: what only the engine needs goes in `engine/AGENTS.md`. `.github/copilot-instructions.md` is a condensed copy for the Copilot features that read only that file; when a rule changes here, update it there too.

## What this is

graphlore is a Python MCP server that makes a code knowledge graph (`graphify-out/graph.json`) navigable and joins it to real source spans. Building the graph is its native engine's job (`engine/`, the `engine` extra) by default, with the external `graphify` CLI (PyPI `graphifyy`, deprecated) as the fallback when the engine is not installed.

`engine/` is graphlore's own extractor, written in Rust: a separate distribution, `graphlore-engine` (import name `graphlore_engine`), built with maturin + PyO3 with its grammars compiled in and installed from prebuilt PyPI wheels (`.github/workflows/engine-wheels.yml`). It is the default (`GRAPHLORE_ENGINE=auto`: native when installed, graphify otherwise; `native` forces it); `docs/native-engine.md` says what it extracts in 14 languages and the roadmap (graphify goes in the next release). graphlore itself stays pure Python: the Claude Code plugin builds it from source on the user's machine, so Rust must never enter its own build (`pyproject.toml` excludes `engine/` from the sdist).

It is built on the **MCP Python SDK v2** (`mcp>=2.1,<3.0`): `mcp.server.mcpserver.MCPServer`, not v1's `FastMCP`, and `ToolAnnotations` with snake_case fields (`read_only_hint`, `destructive_hint`).

## Commands

```bash
pip install -e ".[dev,treesitter]"   # or: uv sync --extra dev --extra treesitter, then prefix commands with `uv run`

ruff check .
mypy                                 # configured in pyproject.toml, checks src/graphlore
pytest -q
pytest -q tests/test_tools.py::test_overview_json   # one test
pytest -q -k freshness                              # by keyword
pytest -q --cov --cov-report=term-missing           # what CI runs; coverage floor is 80%

python benchmarks/polyglot.py --setup --root /tmp/polyglot   # clone the 45 audit repos (--set 1 / --set 2), build their graphs
python benchmarks/polyglot.py --root /tmp/polyglot --baseline benchmarks/results-polyglot.json   # every tool on each; new / gone findings

GRAPHLORE_PROJECT_DIR=/path/to/repo python -m graphlore   # run the server (stdio)

# the native engine (engine/), with a Rust toolchain; its benchmarks and oracles are in engine/AGENTS.md
cargo fmt --manifest-path engine/Cargo.toml --check
cargo clippy --manifest-path engine/Cargo.toml --all-targets -- -D warnings
cargo clippy --manifest-path engine/Cargo.toml --all-targets --features python -- -D warnings
cargo test --manifest-path engine/Cargo.toml
maturin build -m engine/Cargo.toml --release --out dist-engine && pip install dist-engine/*.whl   # or `maturin develop` in a venv
```

CI (`.github/workflows/ci.yml`) runs `ruff check .`, `mypy` and pytest with coverage on Python 3.10–3.12, so code must stay 3.10-compatible; its `engine` job runs the cargo checks, builds the wheel and runs the suite with the engine installed. The default branch is `master`. Unlike the Python sources, `engine/` is `cargo fmt`-formatted (`engine/rustfmt.toml`) and CI checks it.

**Don't run `ruff format .` across the repo.** CI doesn't check formatting and most of the Python files (including `server.py` and `tests/test_tools.py`) are not ruff-formatted, so it rewrites them wholesale. Match the surrounding style by hand unless a reformat is the task.

The multi-language tests skip without the `[treesitter]` extra. With it, `tree-sitter-language-pack` downloads grammars from GitHub releases on first use (cached under `~/.cache/tree-sitter-language-pack/`); if that download fails, those tests **fail** (`assert None is True`, `KeyError`, empty route lists), which looks like a real regression in the extractors. Check first:

```bash
python -c "from tree_sitter_language_pack import get_language; get_language('javascript')"
```

A `LanguageNotFoundError: Download error` means the failures are environmental; if it succeeds, they are real.

## Architecture

`src/graphlore/` is layered bottom → top; each module imports only from earlier entries in this list (plus one sideways import: `routes.py` uses `_strip_quotes` from `apis.py`). `__main__.py` runs `cli.main()`; `viewer.html` is the page `viz.py` fills.

- `agents_md.py` — the usage guide for agents that read a project file (AGENTS.md, GEMINI.md, Copilot's instructions): `render(tools)` names only the toolset's tools, between `<!-- graphlore:begin -->` / `<!-- graphlore:end -->`; `merge` replaces only that part of a file. Imports nothing from graphlore.
- `clients.py` — the MCP clients `graphlore setup` knows (`CLIENTS`: config files, JSON key or Codex's TOML, the file its agent reads, its add command), `render` (the block to paste) and `write` (merge after a `.graphlore.bak`, keeping every other server; refuse a file it cannot parse). Imports nothing from graphlore. A client format changes only with its page re-read (`docs/clients.md` cites them).
- `config.py` — `env(name)` reads `GRAPHLORE_<name>`, falling back to the legacy `GRAPHIFY_<name>`; holds `PROJECT_DIR` and `OUT_DIR_NAME`, `offline()` and `export_offline_env()` (the offline switch, and the variables it sets for libraries that download), and `PROJECT_FROM_CLIENT` / `project_pending` (a project the client names, below).
- `oauth.py` — OAuth for the HTTP transport, graphlore as a resource server: `settings()` reads `GRAPHLORE_AUTH_ISSUER` / `AUTH_RESOURCE_URL` / `AUTH_SCOPES`, `JwtVerifier` checks tokens against the provider's JWKS (found by discovery; asymmetric algorithms only; `iss` / `aud` / `exp` required), `apply(mcp, conf)` wires it into the SDK before `main()` builds the HTTP app. pyjwt (`remote` extra) is imported only when configured; the key fetch is network egress (refused offline). Imports only `config`.
- `engine.py` — the extractor choice (`GRAPHLORE_ENGINE`, read per call): `choose()` routes a build to graphify or the native engine, `build()` runs `python -m graphlore_engine build` (`--incremental` for `update=True`) and `cluster()` runs `... cluster` (for `cluster_only=True`) in a child process (a grammar crash cannot take the server down), `render_report()` is the build reply, `file_spans()` is the span fallback `spans.py` uses when Python tree-sitter is missing. It never imports `graphlore_engine` at module import.
- `graph.py` — loads `graph.json` (cached by path + mtime), schema-tolerant node/edge accessors, adjacency, BFS, SCC cycles, hop distances, surprise scoring, shared state (`_STATE_RELATIONS`, `_COUPLING_RELATIONS`, `_shared_state`, `_engine_pairs`, `_with_written_by`), HTTP (`_HTTP_RELATIONS`, `_is_route_node`, `_native_routes`), token estimation. No MCP dependency.
- `algorithms.py` — graph algorithms over plain adjacency maps, no graph.json knowledge: `certain_route` (`graphlore_path`), `pagerank` / `betweenness` (`graphlore_god_nodes`' `rank=`), `dominators` / `dominated_counts` (`graphlore_impact`'s `chokepoints`), `cut_structure` (`graphlore_bridges`). Deterministic: ties follow the order of the lists handed in, samples a hash of the id. Imports nothing from graphlore; checked against networkx on 300 random graphs.
- `history.py` — files that change together, from one local `git log` (the last 1000 non-merge commits, renames followed, commits of more than 30 files skipped; code-maat's degree), cached on `(PROJECT_DIR, HEAD)`. A shallow clone or a history under 10 commits is reported (`History.note()`), never read as "nothing changes together". No network.
- `spans.py` — the span engine: per-file `(region_start, end_line, def_line, qualname)` spans, `_node_for_location` (semantic chunk → enclosing graph node), `_structurally_equal` (the cosmetic-vs-structural diff behind freshness/diff/watch), and the shared per-file pipeline `_cached_file_analysis`.
- `scope.py` — the analysis scope shared by the analysis tools: parses the `scope` string, detects vendored/minified files, and hands back a cached `ScopeView` of the nodes and edges it keeps.
- `apis.py`, `routes.py` — per-file extractors (external package API usage; framework route → handler) built on the `spans.py` pipeline.
- `imports.py` — import statements read from the importing file's source (Python via `ast`, JS/TS via tree-sitter): `ImportChecker.kind` says when the import behind a file-level import edge runs (module-level, deferred, type-checking) and rejects an edge the source contradicts (`import yaml` linked to a first-party `yaml.py`).
- `resolve.py` — edges the graph lacks and the source proves: `_resolved(nodes, edges)` returns the graph's edges plus calls and imports made through a module object (`mod.func()`; Python, plus JS/TS default and dynamic imports), marked `resolved_by: "graphlore"`, as one cached list.
- `review.py` — the review analyses with no MCP dependency: unreferenced code, same-named symbols, identical bodies, layer rules.
- `viz.py` — `graph.html`, graphlore's own offline view: `page_data` compacts graph.json (relations grouped by `relation_group`), `render` puts it into `viewer.html` (plain JavaScript, a CSP that allows no request), `write` skips a graph over `MAX_NODES`. Written after every build (`no_viz=True` skips it), `cluster_only`, `graphlore_set_labels` and `graphlore_prune` (graphify's own graph.html is only patched, `viz.is_ours`). Repository text is embedded with `<`, `>`, `&` escaped and shown with `textContent` / `fillText` only. `source_of_remote` gives the "On GitHub ↗" link (host and repository path only, never a user name or token). Two JavaScript twins change with their Python side: `compact()` (`// compact:begin` / `end`, with `RELATION_GROUPS`) of `page_data`, for the page's "Open graph.json" button, checked by `test_the_viewer_reads_a_raw_graph_as_python_does` (also `IMPACT_NEVER` / `IMPACT_FROM_STATE`); and `impactOf` (`// impact:begin` / `end`) of `graphlore_impact`, checked on every node by `test_graph_html_shows_what_graphlore_s_tools_find`. `page_data`'s `analysis` (cycles, surprises, unreferenced, vendored files, `_resolved`'s edges) is `server._viz_analysis`, cached on (path, mtime); a failing tool is a line of `notes`, never a missing page. `.github/workflows/pages.yml` publishes the viewer to GitHub Pages. Imports only `graph`.
- `embed.py` — the optional dense tier of the built-in search: loads a model2vec static model (`[embed]` extra) behind `config.export_offline_env()`, and `VectorStore` keeps chunk vectors by text hash (in memory, and on disk under `GRAPHLORE_CACHE_DIR`, never in the project). Imports only `config`.
- `search.py` — graphlore's own code search, the `graphlore_locate` / duplication-scan backend when semble is absent: one chunk per span-engine definition, BM25F over name / path / body plus a graph overlay, the dense tier fused by reciprocal rank. `index_for_project()` keeps one `CodeIndex` per (`PROJECT_DIR`, model), refreshed per file. The hot loops sit behind `_Kernel`; `tests/fixtures/search_golden.json` is the contract an accelerator must meet bit for bit.
- `server.py` — the whole MCP surface in one ~8,000-line module: the `mcp` instance, 34 tools, resources, prompts, toolset trimming, the opt-in watcher, the HTTP transports' auth (a bearer key, or `oauth.apply`) and `main()`.
- `cli.py` — the `graphlore` console script: no arguments runs `server.main()` (the plugin, `mcp.json` and `server.json` start it so; never add a required argument), `setup <client>`, `clients`, `agents-md`. It imports `server` only to run it or to name the toolset's tools.

Tools come in two kinds. **CLI-backed** tools (`build`, `add`) shell out through `_run_cli` (`build` goes to `_build_native` when `engine.choose` picks the native engine), always as an argv list with no shell; failure is the `ERROR` prefix of the returned string. Every other tool, `query`, `path` and `explain` included, reads graph.json directly and must keep working with no `graphify` binary and no optional extras; community naming is sampling or `graphlore_set_labels` only (`method="cli"` is refused).

Optional dependencies (`semble`, `model2vec`/`numpy` for `[embed]`, `tree-sitter`, `tiktoken`, `watchdog`, `uvicorn`, `jwt` (pyjwt, the `remote` extra), `graphlore_engine`, and `graphlore_accel` if present) are imported lazily inside functions and degrade to a fallback or an install hint; nothing may raise `ImportError` at module import.

## Conventions that span files

- **Read `config.PROJECT_DIR` by attribute**, never `from .config import PROJECT_DIR`: tests repoint it with `monkeypatch.setattr(server.config, "PROJECT_DIR", tmp_path)`, and `graphlore_project` reassigns it at runtime. For the same reason nothing may cache a value derived from it without keying on it. Under `GRAPHLORE_PROJECT_FROM_CLIENT` (a plugin started in its own directory) `config.project_pending` is True until the client's roots or `graphlore_project` name the project, and `_tool`'s wrapper answers every tool but `_PROJECT_FREE_TOOLS` with `code: project_unknown` meanwhile (a direct call skips the check).
- **Settings go through `config.env("NAME")`** so the legacy `GRAPHIFY_*` fallback applies. Several are captured once at import as `server.py` module constants (`TOOLSET`, `TRANSPORT`, `RESTRICT_PATHS`, `API_KEY`, `GRAPHIFY_BIN`, …) and tests patch the attribute; others (`SEMANTIC_BACKEND`, `WATCH`, `ALLOWED_HOSTS`, `TOKENIZER`, `OFFLINE` via `config.offline()`, `STRUCTURED`, `ENGINE` via `engine.requested()`) are read at call time.
- **Network egress:** every path that can reach the network checks `config.offline()` (refuse, or degrade to a local-only variant and say so); the "What reaches the network, and when" table in `docs/configuration.md` lists them and must stay in step. `_run_cli` passes `_cli_env()`, which strips the `_BACKEND_ENV` keys offline. A new optional dependency that downloads on first use gets a row there and a gate.
- **Repository text is framed:** a tool whose text reply quotes source, docstrings or CLI output derived from them wraps it in `_frame_repo_text(...)` and puts `content_trust: _CONTENT_TRUST` and `untrusted_fields` in the payload. graphlore's own notes go outside the frame; errors are never framed.
- **Tool shape:** a plain sync function returning `str` (the SDK runs sync tools in a threadpool), registered with `@_tool(annotations=...)`, never `@mcp.tool`. `_load_graph()` returns either the graph dict or an error *string*; check `isinstance(graph, str)` and return `_err(msg, as_json)`. Success returns `_fmt(payload, as_json, text)`. With `as_json=True` every path, including errors and no-match, must return parseable JSON.
- **MCP results:** `_tool` registers a wrapper (no outputSchema) and leaves the module attribute as the plain function, so tests get the string. `_fmt` / `_err` record their payload in a per-call `ContextVar`, which becomes the result's `structuredContent` when the tool returns exactly that string. `_err` sets `isError`, as does `_fmt(..., is_error=True)` for a failure with a payload; an empty but valid answer is `_fmt`. `_err(msg, as_json, **extra)` keeps `error` a string and adds sibling keys (`code`, `did_you_mean`). A reply built without `_fmt`/`_err` has no structuredContent and is an error only when it starts with `ERROR`; CLI passthroughs go through `_cli_reply`. `GRAPHLORE_STRUCTURED=0` turns all of this off.
- **The one async tool** is `graphlore_label_communities` (`async def`, takes `ctx: Context` and a keyword-only `Resolve` parameter that must have no default; see the comment on its signature). An async body runs on the event loop, so any blocking work added there goes through `anyio.to_thread.run_sync`. Tests drive it over an in-memory session (`_run_in_memory`), not by calling it directly.
- **Schema tolerance:** graphify's `graph.json` shape varies. For id, label, file, line, edge endpoints and relation use the accessors: `_nodes_edges`, `_node_id`, `_node_label`, `_node_file`, `_node_line`, `_node_type` (`type`, else graphify 0.9's `file_type`), `_edge_ends`, `_edge_rel`. Fields without an accessor are read with `.get()` and a fallback, never `[]`; community is `n.get("community", n.get("cluster"))`. Relation names are compared against the sets in `graph.py` (`_IMPORT_RELATIONS`, `_CALL_RELATIONS`, `_CONTAINMENT_RELATIONS`, …), never against a literal: extractors add relations between releases, and `benchmarks/polyglot.py` reports any that no set names.
- **Ambiguous labels are qualified by `_display_labels(nodes)`** (`DigestAuth.auth_flow()` or a `file:line` suffix). Use it for nodes named in edge, neighbor and list rows. A row that prints its own `file:line` column uses `labels.name(id)` instead, which never adds a location suffix. The resolved subject of a call (`center`, `node`, `seed` in the payload) keeps its bare `_node_label`.
- **Import edges go through `ImportChecker`.** graphify resolves imports by name, so a tool that lifts import edges to file level (`_file_import_edges`, `_module_import_adjacency`) passes `ImportChecker().kind` — one instance per call — and reports `checker.rejected` rather than silently trusting or dropping edges. It reads Python with `ast` and JS/TS with tree-sitter (following an import through a re-exporting `index.ts` to the file graphify linked it to), treats compile-time languages (Go, Java, Kotlin, Scala, C#, Rust, Swift, C, C++, Objective-C) and PHP as module-level, and returns `unclassified` (kept, counted as module-level) for anything else. A new source reader, here or in `resolve.py`, covers every language the project already parses or says per language why there is nothing to read — the `apis.py` extractors are the model.
- **Identity-keyed caches:** `_adjacency`, `_directed_adjacency`, `_edge_set`, `_exact_node_index`, `_name_index`, `_edge_flags`, `_nodes_by_file` and `_display_labels` are keyed on `id()` of the nodes/edges list that `_load_graph` hands back. Pass those lists through unchanged; a copied or filtered list misses the cache on every call. The sanctioned derived lists are `_resolved(...)`'s and a `ScopeView`'s (`_scoped` returns the same objects per graph, and the original lists when the scope leaves nothing out).
- **Implicit coupling is stated per pair.** `_shared_state` gives each writer × other toucher pair its `call_path` (calls, dispatch and HTTP, 6 hops, on the resolved edges) and `co_change`. On a native graph of schema 6+ the state node's `coupling.listed` is the engine's answer (`_engine_pairs`), and `_shared_state` looks for a path only for a pair it does not list: same rules on both sides (`test_native_implicit_coupling_matches_the_python_reading`). A `couples_with` edge is in `_COUPLING_RELATIONS` and so `_NON_DEPENDENCY_RELATIONS`: never a reference, cycle or surprise of its own; `graphlore_impact` walks it only when state is asked for. Code that reads co-change goes through `History.coupled` / `partners` / `coupled_pairs`, and a reply that uses the history carries `history` (`commits`, `shallow`, `skipped_bulk`, `note`).
- **Name resolution:** every tool that takes a node name (impact, subgraph, neighbors, tests_for, node_details, fetch, skeleton) resolves it with `_pick_node`, reports `_matched(key, picked)` (several matches, or a substring fallback, which is never silent) and answers a miss with `_not_found(nodes, key, as_json)`, which adds `code: "not_found"` and `did_you_mean`. Don't call `_resolve_node` from a tool.
- **A cut says what it left out:** a budget or limit that drops rows reports `truncated` plus a count or the names left out (`not_fetched`, `files_left_out`, `total`, `counts`, `beyond_hops`) and a one-line `hint` on how to get the rest (`_cut_hint(payload, "...")`). Never cut silently. The same goes for a language nobody reads: `graphlore_package_apis` and `graphlore_routes` count the source files they have no extractor for in `not_read` (`_not_read(files)`).
- **Spans are generic, and checked on real code.** `spans.py` walks any tree-sitter grammar: a node is a definition when its type carries a hint word and it names itself (a `name` field, a C/C++ declarator chain, or an identifier child in a grammar without name fields). A type merely written in a signature is not a definition. Several spans can start on one line, so a node's own span is `_span_of_definition(file, line, bare name)`, not the innermost one. Whether a node is test code is `_is_test_node(n)` — a test path, or a Rust `#[cfg(test)]` / `#[test]` region of a source file (a module or a function under the attribute) — not `_is_test_path` of its file. After changing the rules, run `benchmarks/polyglot.py` (below): the unit tests hold a few lines per language, the audit holds whole repositories.
- **Node-centric tools** (impact, subgraph, neighbors, tests_for) resolve their node as above; they read `_nav_view(nodes, edges, scope, as_json)`, which is the resolved edge list under a scope that leaves nothing out by default; they order rows production-before-tests; and an empty result carries `_EMPTY_NOTE`. `_resolved` edges are never written back: `graphlore_prune` and `graphlore_validate`'s lint read the raw graph.
- **Analysis scope:** a tool that ranks or audits the graph takes `scope: str = ""` and goes through `_scope_view(nodes, edges, scope, as_json)`. Compute on `view.nodes` / `view.edges`, label with `_display_labels(all_nodes)`, put `view.payload()` under `"scope"` and wrap the text in `_with_note(text, view)` so what was left out is always stated. The default leaves out vendored/minified files and external nodes.
- **Path confinement:** the per-file analyzers and source hydration (spans, APIs, routes, `fetch`, `skeleton`, `prune`) resolve every path from the graph, a semantic chunk or a file/node argument through `spans._resolve_in_project`, usually via `_cached_file_analysis` or `_read_source_lines`. Don't open such paths directly. Three things sit outside it on purpose: `graphlore_build`'s `path` is unconfined by default (absolute and sibling-repo paths are a documented use) and is guarded only by the opt-in `_path_escapes_project` (`RESTRICT_PATHS`, forced on for HTTP transports); `graphlore_project` accepts any directory and is refused outright under `RESTRICT_PATHS`; and freshness/diff/watch read git-reported paths relative to `config.PROJECT_DIR`. `review._count_mentions` walks the project directory itself (like `_route_candidate_files`) and never follows a link out of it.
- **`server.py` re-exports private helpers** from the lower modules (`# noqa: F401`) because tests reach them as `server._x`. A new helper that tests use that way needs adding to the re-export block.
- **stdout is the protocol on stdio transport**; diagnostics (boot banner, warnings, watcher logs) go to stderr.
- **Naming:** `graphlore_*` tools and `GRAPHLORE_*` variables belong to this project. `graphify-out/`, `.graphify_labels.json` and the `graphify` binary are artifacts of the wrapped CLI and keep their names.

## When adding or changing a tool

A tool is registered with `@_tool(annotations=ToolAnnotations(...))` in `server.py`; keep it read-only unless it genuinely mutates state and set the matching hint. The change also touches:

- the tool list in the `server.py` module docstring, and `LEAN_TOOLS` / `LOCATE_TOOLS` if it belongs in a trimmed surface. `lean` is the default surface, so a tool outside it is invisible to most users unless they set `GRAPHLORE_TOOLSET=full` (the plugin does)
- `_instructions(active)` and the prompts (`_render_prompt` steps) if the tool belongs in the recommended flow: they name a tool only when it is registered. A reply that points to another tool wraps the pointer in `_tool_hint(name, text)`
- `test_tool_and_prompt_registration` in `tests/test_tools.py`, which asserts the exact tool count (34)
- the tool tables in `docs/tools.md`, the README's table of the 12 `lean` tools if the tool is in that set, and the "34" / "12" counts in both, and wherever else they are written: `server.json`'s description, `docs/clients.md`, `docs/configuration.md`, `benchmarks/polyglot.py` and the second count in `tests/test_tools.py` (`grep -rn '\b34\b'`)
- `agents_md._FLOW` if the tool belongs in the guide `graphlore agents-md` writes; then regenerate the Gemini extension's context file (`graphlore agents-md --toolset full > .gemini-extension/GRAPHLORE.md`), which `test_plugin_manifests_stay_in_sync` compares with `agents_md.render` of the full toolset
- its docstring: a description of at most 900 characters (what it is for, what the reply carries) and an `Args:` entry for every parameter, which `_describe_parameters` moves onto the input schema as each parameter's `description` (`_doc_args`); parameters stay plain types (a mapping is a JSON string with `_JSON_OBJECT_ARG` and `_json_object`, an optional number a sentinel default, never `X | None`). two tests hold the clients' limits (`test_every_parameter_has_a_description_and_descriptions_stay_short`, `test_input_schemas_use_what_every_function_calling_api_takes`; `docs/clients.md` has the numbers)
- `skills/graphlore-explore/SKILL.md` (shipped to users by every plugin; `.claude/skills/graphlore-explore` is a link to it for this repository's own sessions)
- `CHANGELOG.md` under `[Unreleased]` — every behavior change gets an entry there (Keep a Changelog format)

The version is duplicated in `pyproject.toml`, `server.__version__`, `.claude-plugin/plugin.json`, `plugin.json`, `gemini-extension.json` and `server.json` (twice there; tests compare all but the first), and recorded in `uv.lock`; run `uv lock` after a bump. The release steps, including the PyPI publish workflow, are under "Releasing" in `CONTRIBUTING.md`.

## Documentation layout

`README.md` is the landing page, and PyPI's long description: what graphlore is, quick start, the 12 `lean` tools, the benchmark headline and an FAQ. Keep it short; detail goes to `docs/`:

- `docs/tools.md` (all 34 tools, resources, prompts, results), `docs/concepts.md` (resolved edges, import checks, scope, freshness, search, communities), `docs/configuration.md` (running, plugins, toolsets, transports, the network table, environment variables), `docs/clients.md` (each MCP client's config and limits, with the page each was read from; `graphlore setup` / `agents-md`)
- benchmarks: `docs/benchmark.md` (`locate` and search; `docs/benchmark*.html` are rendered reports), `docs/benchmark-polyglot.md` (every tool on 31 + 14 repositories; `benchmarks/results-polyglot.json` is set 1's baseline), `docs/benchmark-agents.md` (coding agents on httpx; `benchmarks/agents/`, run by hand with each agent's login, never in CI)
- the engine: `docs/native-engine.md` (what it extracts, the comparison with graphify, the roadmap), `docs/resolution-rules.md` (generated by `benchmarks/conformance.py --markdown`), `docs/rule-sources.md` (where the rules are read from)

Links from the README into the repository are absolute (`https://github.com/yasinyaman/graphlore/blob/master/...`) because relative links break on PyPI; links between the `docs/` files are relative. The README's first paragraph and its FAQ headings are written to be quoted by search engines and AI assistants: keep them plain, literal and true to the code.

## MCP Registry entry

`server.json` at the root is the manifest for the official MCP Registry (schema `2025-12-11`). Its `name` (`io.github.yasinyaman/graphlore`) must also appear as `mcp-name: ...` in `README.md`: the registry verifies PyPI ownership by finding that string in the package's README, so the HTML comment under the README title is load-bearing. The description is limited to 100 characters, the environment variables it lists must be ones the server reads, and its toolset choices must match `TOOLSETS`; `test_mcp_registry_manifest_stays_in_sync` checks all of this. Publishing is a manual step after a PyPI release (see "Releasing" in `CONTRIBUTING.md`).

## Plugins

The repository root is itself a plugin, in three formats, and its own marketplace:

- **Claude Code:** `.claude-plugin/plugin.json` and `.claude-plugin/marketplace.json` (`"source": "./"`). Codex and Copilot CLI read that marketplace file too.
- **Agent Plugins 1.0** (Codex, Copilot CLI; Cursor by its documentation): `plugin.json` at the root (a closed schema: `$schema`, `name`, `version`, `description`, `author`, `homepage`, `repository`, `license`, `keywords`, `extensions` only), `mcp.json` (the spec's format, `type: stdio`, started in the plugin root, so `uvx --from "graphlore[…] @ ."`) and `skills/`, a fixed location. The spec is `agentplugins/agent-plugins-spec` on GitHub.
- **Gemini CLI:** `gemini-extension.json` (`${extensionPath}`, `${workspacePath}`) with `.gemini-extension/GRAPHLORE.md` as its context file, which is `agents_md.render` of the full toolset. Without `contextFileName` Gemini would load the root `GEMINI.md`, this repository's own guide, into every user's session.

Consequences:

- `skills/` is what every plugin ships to users. Anything added there is installed for everyone.
- Every manifest's MCP server runs `uvx --from "graphlore[engine,graphify,treesitter,semble,embed] @ <its own copy>" graphlore`, i.e. it builds this package from the installed copy of the repo. Renaming the console script, the package or those extras breaks the plugins. `test_plugin_manifests_stay_in_sync` holds the versions, the extras, the skill path and the Gemini context file together.
- An Agent Plugins client names no project: `mcp.json` sets `GRAPHLORE_PROJECT_FROM_CLIENT=1` and never `GRAPHLORE_PROJECT_DIR` (see the conventions above).
- Users stay on a manifest's `version` until it changes, so a fix reaches plugin users only with a version bump.
- Check manifest changes with `claude plugin validate --strict .`; it passes clean.
- Claude Code's project instructions live in `.claude/CLAUDE.md`, not at the root. A `CLAUDE.md` at a plugin root is not loaded as plugin context and makes the validator warn, so don't add one there.

## The native engine (`engine/`)

Its own rules, benchmarks and oracles are in [`engine/AGENTS.md`](engine/AGENTS.md): read it before changing anything under `engine/`. What ties it to the Python side:

- Kept in step, a change in one is a change in the other: `engine/src/generic.rs` and `spans.py`'s definition rule, `parse.rs`'s and `spans.py`'s `blank_*` rules (`tests/test_engine.py` compares `file_spans` per language), `engine/src/coupling.rs` and `graph._shared_state`, `engine/src/http/` and `routes.py`.
- graph.json keeps graphify's shape (node-link, path-slug ids, a file hub per file, `source_location`); the engine adds keys, never `type` or `line` on code nodes. A graph whose header says `engine: graphlore` and `schema_version` ≥ 2 is engine-resolved (`graph._engine_resolved`): `resolve._resolved` adds nothing to it, and `ImportChecker.kind` takes its import edges' `runs` as given.
- The engine's version lives only in `engine/Cargo.toml`; `SCHEMA_VERSION` (`engine/src/lib.rs`) must be in `engine.SUPPORTED_SCHEMAS` (`test_engine_version_pins_stay_in_sync`). The `engine` extra pins its minor (`>=0.5.79,<0.6`): an engine release graphlore needs is published first (an `engine-vX.Y.Z` tag), then the pin and `uv lock` follow.
- The engine never reaches the network, and graphlore's own build never needs Rust.

## Tests

Everything is in `tests/test_tools.py`, except the native engine's end-to-end tests (`tests/test_engine.py`, skipped without `graphlore_engine`) and its Rust tests (`engine/tests/`). An autouse fixture clears `GRAPHLORE_ENGINE`; `tests/conftest.py` pins `server.TOOLSET = "full"` (`server.main()` trims the shared `server.mcp` for real, and the default is `lean`). Tests call tool functions directly (`server.graphlore_overview(as_json=True)`) and parse the result. The `project` fixture is a temp project with the 5-node fixture graph, `empty_project` has none; a test needing another shape writes its own `graphify-out/graph.json` into `tmp_path` and repoints `PROJECT_DIR`. Protocol-level behavior uses the SDK's in-memory `Client(server.mcp)` under `asyncio.run` (no pytest-asyncio). Freshness/diff tests build a real git repo in `tmp_path`.
