# AGENTS.md

Guidance for AI coding agents working in this repository. This file is the single source: Codex, Cursor and Copilot's agent features read it directly, and `.claude/CLAUDE.md` and `GEMINI.md` import it. `.github/copilot-instructions.md` is a condensed copy for the Copilot features that read only that file; when a rule changes here, update it there too.

## What this is

graphlore is a Python MCP server that makes a Graphify-built knowledge graph (`graphify-out/graph.json`) navigable and joins it to real source spans. By default building the graph is delegated to the external `graphify` CLI (PyPI package `graphifyy`). What lives in `src/graphlore/` is graph analysis plus the span engine (stdlib `ast` for Python, tree-sitter for everything else).

`engine/` is graphlore's own extractor, written in Rust: a separate distribution, `graphlore-engine` (import name `graphlore_engine`), built with maturin + PyO3, with its tree-sitter grammars compiled in. It is experimental and opt-in (`GRAPHLORE_ENGINE=native` or `auto`): for 14 languages it writes files, definitions with their `start..end` spans, properties and constants, containment (`contains` / `method` / `defines` / `case_of`), Markdown/RST headings, the imports, calls, bases and type references it resolves from the source, shared state (variables, fields, constants and resources such as environment variables, files, tables and events, with the `reads` / `writes` of the definitions that touch them), and communities of its own (Leiden on edges weighted by kind, confidence and directory); `update=True` parses only the files that changed. The plan is to make it the default once `benchmarks/compare_engines.py` and the polyglot audit say it matches graphify, then drop graphify. graphlore itself stays pure Python: the Claude Code plugin builds it from source on the user's machine, so Rust must never enter its own build (`pyproject.toml` excludes `engine/` from the sdist).

It is built on the **MCP Python SDK v2** (`mcp>=2.1,<3.0`): `mcp.server.mcpserver.MCPServer`, not v1's `FastMCP`, and `ToolAnnotations` with snake_case fields (`read_only_hint`, `destructive_hint`).

## Commands

```bash
pip install -e ".[dev,treesitter]"   # or: uv sync --extra dev --extra treesitter, then prefix commands with `uv run`

ruff check .
mypy                                 # configured in pyproject.toml, checks src/graphlore
pytest -q
pytest -q tests/test_tools.py::test_overview_json   # one test
pytest -q -k freshness                              # by keyword
pytest -q --cov --cov-report=term-missing           # what CI runs; coverage floor is 80%

python benchmarks/polyglot.py --setup --root /tmp/polyglot   # clone 45 repos in 14 languages (31 + a second set of 14: --set 1 / --set 2), build their graphs
python benchmarks/polyglot.py --root /tmp/polyglot --baseline benchmarks/results-polyglot.json   # every tool on each; new / gone findings

GRAPHLORE_PROJECT_DIR=/path/to/repo python -m graphlore   # run the server (stdio)

# the native engine (engine/), with a Rust toolchain
cargo fmt --manifest-path engine/Cargo.toml --check
cargo clippy --manifest-path engine/Cargo.toml --all-targets -- -D warnings
cargo test --manifest-path engine/Cargo.toml
maturin build -m engine/Cargo.toml --release --out dist-engine && pip install dist-engine/*.whl   # or `maturin develop` in a venv
python benchmarks/compare_engines.py REPO            # native graph vs graphify's: definitions and edges, per language
python benchmarks/compare_engines.py REPO --communities   # the two engines' communities: size, directory purity, test mixing, NMI
python benchmarks/verify_graphify.py REPO... --baseline benchmarks/results-verify-graphify.json   # graphify's edges checked by the compiler first (Go, Rust, C#); exits 1 when the native graph lacks more of the confirmed ones than the baseline
python benchmarks/polyglot.py --root /tmp/polyglot --engine native   # the audit on native graphs (graphlore-native/)
python benchmarks/unresolved.py --root /tmp/polyglot --samples 5     # the calls the engine left without an edge, by reason (--real: without the library names)
python benchmarks/conformance.py --baseline benchmarks/results-conformance.json   # each language's name-resolution rules, a small project per rule: fixed / broken
python benchmarks/neutrality.py --baseline benchmarks/results-neutrality.json   # every name table in every language: is a project's own `Optional`, `map`, `self` still the project's? (6 min)
python benchmarks/verify_cases.py                 # each case of the checklist, given to its language's own compiler
python benchmarks/oracle_typescript.py TS/tsc/testdata/baselines/reference/compiler   # the engine's edges against what the TypeScript compiler bound (a checkout of microsoft/TypeScript)
python benchmarks/oracle_scala.py SCALA3/tests/semanticdb/expect   # the same against the Scala 3 compiler's SemanticDB expect files (a checkout of scala/scala3)
python benchmarks/oracle_kotlin.py KOTLIN/analysis/analysis-api/testData/components/resolver/allByPsi   # against the Kotlin compiler's resolver tests (a checkout of JetBrains/kotlin)
python benchmarks/oracle_swift.py SWIFT/test/Index   # against the Swift compiler's index tests (a checkout of swiftlang/swift)
python benchmarks/oracle_go.py REPO...     # the engine's Go edges against go/types on whole repositories (needs go and the module proxy once)
python benchmarks/oracle_rust.py REPO...   # the same against `rust-analyzer lsif` (rustup component add rust-analyzer)
python benchmarks/oracle_csharp.py REPO... # the same against Roslyn (needs dotnet and, once, the Microsoft.CodeAnalysis.CSharp package)
```

CI (`.github/workflows/ci.yml`) runs `ruff check .`, `mypy` and pytest with coverage on Python 3.10–3.12, so code must stay 3.10-compatible; its `engine` job runs the cargo checks, builds the wheel and runs the suite with the engine installed. The default branch is `master`. Unlike the Python sources, `engine/` is `cargo fmt`-formatted (`engine/rustfmt.toml`) and CI checks it.

**Don't run `ruff format .` across the repo.** CI doesn't check formatting and 8 of the 11 Python files (including `server.py` and `tests/test_tools.py`) are not ruff-formatted, so it rewrites them wholesale. Match the surrounding style by hand unless a reformat is the task.

The multi-language tests skip themselves when the `[treesitter]` extra is absent. When it is installed, `tree-sitter-language-pack` downloads grammars from GitHub releases on first use (cached under `~/.cache/tree-sitter-language-pack/`); if that download fails, those tests **fail** rather than skip (`assert None is True`, `KeyError`, empty route lists). Those symptoms look the same as a real regression in the tree-sitter extractors, so check before dismissing them:

```bash
python -c "from tree_sitter_language_pack import get_language; get_language('javascript')"
```

A `LanguageNotFoundError: Download error` means the grammars are unavailable and the failures are environmental. If it succeeds, the failures are real.

## Architecture

`src/graphlore/` is layered bottom → top; each module imports only from earlier entries in this list (plus one sideways import: `routes.py` uses `_strip_quotes` from `apis.py`):

- `config.py` — `env(name)` reads `GRAPHLORE_<name>`, falling back to the legacy `GRAPHIFY_<name>`; holds `PROJECT_DIR` and `OUT_DIR_NAME`.
- `engine.py` — the extractor choice (`GRAPHLORE_ENGINE`, read per call): `choose()` routes a build to graphify or the native engine, `build()` runs `python -m graphlore_engine build` (`--incremental` for `update=True`) and `cluster()` runs `... cluster` (for `cluster_only=True`) in a child process (a grammar crash cannot take the server down), `render_report()` is the build reply, `file_spans()` is the span fallback `spans.py` uses when Python tree-sitter is missing. It never imports `graphlore_engine` at module import.
- `graph.py` — loads `graph.json` (cached by path + mtime), schema-tolerant node/edge accessors, adjacency, BFS, SCC cycles, hop distances, surprise scoring, shared state (`_STATE_RELATIONS`, `_shared_state`, `_with_written_by`), HTTP (`_HTTP_RELATIONS`, `_is_route_node`, `_native_routes`), token estimation. No MCP dependency.
- `history.py` — files that change together, from one local `git log` (the last 1000 non-merge commits, renames followed, commits of more than 30 files skipped; code-maat's degree), cached on `(PROJECT_DIR, HEAD)`. A shallow clone or a history under 10 commits is reported (`History.note()`), never read as "nothing changes together". No network.
- `spans.py` — the span engine: per-file `(region_start, end_line, def_line, qualname)` spans, `_node_for_location` (semantic chunk → enclosing graph node), `_structurally_equal` (the cosmetic-vs-structural diff behind freshness/diff/watch), and the shared per-file pipeline `_cached_file_analysis`.
- `scope.py` — the analysis scope shared by the analysis tools: parses the `scope` string, detects vendored/minified files, and hands back a cached `ScopeView` of the nodes and edges it keeps.
- `apis.py`, `routes.py` — per-file extractors (external package API usage; framework route → handler) built on the `spans.py` pipeline.
- `imports.py` — import statements read from the importing file's source (Python via `ast`, JS/TS via tree-sitter): `ImportChecker.kind` says when the import behind a file-level import edge runs (module-level, deferred, type-checking) and rejects an edge the source contradicts (`import yaml` linked to a first-party `yaml.py`).
- `resolve.py` — edges the graph lacks and the source proves: `_resolved(nodes, edges)` returns the graph's edges plus calls and imports made through a module object (`mod.func()`; Python, plus JS/TS default and dynamic imports), marked `resolved_by: "graphlore"`, as one cached list.
- `review.py` — the review analyses with no MCP dependency: unreferenced code, same-named symbols, identical bodies, layer rules.
- `embed.py` — the optional dense tier of the built-in search: loads a model2vec static model (`[embed]` extra) behind `config.export_offline_env()`, and `VectorStore` keeps chunk vectors by text hash (in memory, and on disk under `GRAPHLORE_CACHE_DIR`, never in the project). Imports only `config`.
- `search.py` — graphlore's own code search, the default `graphlore_locate` / duplication-scan backend when semble is absent: one chunk per span-engine definition (a container holds only its own lines), identifier-aware BM25F over name / path / body plus a graph overlay (docstring, call-neighbour names), the dense tier fused by weighted reciprocal rank, a path prior and per-file decay. `index_for_project()` keeps one `CodeIndex` per (`PROJECT_DIR`, model) and refreshes it per call by file (mtime, size). The hot loops sit behind `_Kernel` (`tokenize`, `bm25f`); `tests/fixtures/search_golden.json` is the contract an accelerator must meet bit for bit.
- `server.py` — the whole MCP surface in one ~5,000-line module: the `mcp` instance, 33 tools, resources, prompts, toolset trimming, the opt-in watcher, HTTP bearer auth and `main()`.

Tools come in two kinds. **CLI-backed** tools (`build`, `add`, `query`, `path`, `explain`) shell out through `_run_cli` (`build` goes to `_build_native` instead when `engine.choose` picks the native engine), always as an argv list with no shell; `graphlore_label_communities(method="cli")` is a sixth `_run_cli` caller (`graphify label`). Callers detect failure by the `ERROR` prefix of the returned string. **graph.json analysis** tools read the graph directly and must keep working with no `graphify` binary and no optional extras installed.

Optional dependencies (`semble`, `model2vec`/`numpy` for `[embed]`, `tree-sitter`, `tiktoken`, `watchdog`, `uvicorn`, `graphlore_engine`) are imported lazily inside functions and degrade to a fallback or an install hint; nothing may raise `ImportError` at module import.

## Conventions that span files

- **Read `config.PROJECT_DIR` by attribute**, never `from .config import PROJECT_DIR`: tests repoint it with `monkeypatch.setattr(server.config, "PROJECT_DIR", tmp_path)`, and `graphlore_project` reassigns it at runtime. For the same reason nothing may cache a value derived from it without keying on it.
- **Settings go through `config.env("NAME")`** so the legacy `GRAPHIFY_*` fallback applies. Several are captured once at import as `server.py` module constants (`TOOLSET`, `TRANSPORT`, `RESTRICT_PATHS`, `API_KEY`, `GRAPHIFY_BIN`, …) and tests patch the attribute; others (`SEMANTIC_BACKEND`, `WATCH`, `ALLOWED_HOSTS`, `TOKENIZER`, `OFFLINE` via `config.offline()`, `STRUCTURED`, `ENGINE` via `engine.requested()`) are read at call time.
- **Network egress:** every path that can reach the network checks `config.offline()` (refuse, or degrade to a local-only variant and say so); the "What reaches the network, and when" table in `docs/configuration.md` lists them and must stay in step. `_run_cli` passes `_cli_env()`, which strips the `_BACKEND_ENV` keys offline. A new optional dependency that downloads on first use gets a row there and a gate. The native engine never reaches the network (its grammars are compiled in); keep it that way.
- **Repository text is framed:** a tool whose text reply quotes source, docstrings or CLI output derived from them wraps it in `_frame_repo_text(...)` and puts `content_trust: _CONTENT_TRUST` and `untrusted_fields` in the payload. graphlore's own notes go outside the frame; errors are never framed.
- **Tool shape:** a plain sync function returning `str` (the SDK runs sync tools in a threadpool), registered with `@_tool(annotations=...)`, never `@mcp.tool`. `_load_graph()` returns either the graph dict or an error *string*; check `isinstance(graph, str)` and return `_err(msg, as_json)`. Success returns `_fmt(payload, as_json, text)`. With `as_json=True` every path, including errors and no-match, must return parseable JSON.
- **MCP results:** `_tool` registers a wrapper (no outputSchema) and leaves the module attribute as the plain function, so direct calls and tests get the string. `_fmt` / `_err` record their payload in a per-call `ContextVar`; when the tool returns exactly that string, the payload becomes the result's `structuredContent`. `_err` sets `isError`, and so does `_fmt(..., is_error=True)` for a failure that still has a payload. An empty but valid answer (no search hits) is `_fmt`, not `_err`. `_err(msg, as_json, **extra)` keeps `error` a string and adds sibling keys (`code`, `did_you_mean`). A reply built without `_fmt`/`_err` has no structuredContent and is an error only when it starts with `ERROR`; CLI passthroughs go through `_cli_reply`. `GRAPHLORE_STRUCTURED=0` turns all of this off.
- **The one async tool** is `graphlore_label_communities` (`async def`, takes `ctx: Context` and a keyword-only `Resolve` parameter that must have no default; see the comment on its signature). An async body runs on the event loop, so blocking work there goes through `anyio.to_thread.run_sync`. Tests drive it over an in-memory session (`_run_in_memory`), not by calling it directly.
- **Schema tolerance:** graphify's `graph.json` shape varies. For id, label, file, line, edge endpoints and relation use the accessors: `_nodes_edges`, `_node_id`, `_node_label`, `_node_file`, `_node_line`, `_node_type` (`type`, else graphify 0.9's `file_type`), `_edge_ends`, `_edge_rel`. Fields without an accessor are read with `.get()` and a fallback, never `[]`; community is `n.get("community", n.get("cluster"))`. Relation names are compared against the sets in `graph.py` (`_IMPORT_RELATIONS`, `_CALL_RELATIONS`, `_CONTAINMENT_RELATIONS`, …), never against a literal: graphify adds relations between releases (`defines`, `case_of`, `dispatches_to` in 0.9), and `benchmarks/polyglot.py` reports any that no set names.
- **Ambiguous labels are qualified by `_display_labels(nodes)`** (`DigestAuth.auth_flow()` or a `file:line` suffix). Use it for nodes named in edge, neighbor and list rows. A row that prints its own `file:line` column uses `labels.name(id)` instead, which never adds a location suffix. The resolved subject of a call (`center`, `node`, `seed` in the payload) keeps its bare `_node_label`.
- **Import edges go through `ImportChecker`.** graphify resolves imports by name, so a tool that lifts import edges to file level (`_file_import_edges`, `_module_import_adjacency`) passes `ImportChecker().kind` — one instance per call — and reports `checker.rejected` rather than silently trusting or dropping edges. It reads Python with `ast` and JS/TS with tree-sitter (following an import through a re-exporting `index.ts` to the file graphify linked it to), treats compile-time languages (Go, Java, Kotlin, Scala, C#, Rust, Swift, C, C++, Objective-C) and PHP as module-level, and returns `unclassified` (kept, counted as module-level) for anything else. A new source reader, here or in `resolve.py`, covers every language the project already parses or says per language why there is nothing to read — the `apis.py` extractors are the model.
- **Identity-keyed caches:** `_adjacency`, `_directed_adjacency`, `_edge_set`, `_exact_node_index`, `_name_index`, `_edge_flags`, `_nodes_by_file` and `_display_labels` are keyed on `id()` of the nodes/edges list that `_load_graph` hands back. Pass those lists through unchanged; a copied or filtered list misses the cache on every call. The sanctioned derived lists are `_resolved(...)`'s extended edge list and a `ScopeView`'s: `_scoped` builds it once per graph and returns the same objects afterwards (and returns the original lists when the scope leaves nothing out).
- **Implicit coupling is stated per pair.** `_shared_state` gives each writer × other toucher pair its `call_path` (calls, dispatch and HTTP, 6 hops, on the resolved edges) and `co_change`; a hidden pair (no call path) is what scores. `graphlore_surprises`' `co_change` and `graphlore_node_details`' `co_change` read `history.history()`; a reply that uses the history carries `history` (`commits`, `shallow`, `skipped_bulk`, `note`), and code that reads co-change goes through `History.coupled` / `partners` / `coupled_pairs`, not its counts.
- **Name resolution:** every tool that takes a node name (impact, subgraph, neighbors, tests_for, node_details, fetch, skeleton) resolves it with `_pick_node`, reports `_matched(key, picked)` (several matches, or a substring fallback, which is never silent) and answers a miss with `_not_found(nodes, key, as_json)`, which adds `code: "not_found"` and `did_you_mean`. Don't call `_resolve_node` from a tool.
- **A cut says what it left out:** a budget or limit that drops rows reports `truncated` plus a count or the names left out (`not_fetched`, `files_left_out`, `total`, `counts`, `beyond_hops`) and a one-line `hint` on how to get the rest (`_cut_hint(payload, "...")`). Never cut silently. The same goes for a language nobody reads: `graphlore_package_apis` and `graphlore_routes` count the source files they have no extractor for in `not_read` (`_not_read(files)`).
- **Spans are generic, and checked on real code.** `spans.py` walks any tree-sitter grammar: a node is a definition when its type carries a hint word and it names itself (a `name` field, a C/C++ declarator chain, or an identifier child in a grammar without name fields). A type merely written in a signature is not a definition. Several spans can start on one line, so a node's own span is `_span_of_definition(file, line, bare name)`, not the innermost one. Whether a node is test code is `_is_test_node(n)` — a test path, or a Rust `#[cfg(test)]` / `#[test]` region of a source file (a module or a function under the attribute) — not `_is_test_path` of its file. After changing the rules, run `benchmarks/polyglot.py` (below): the unit tests hold a few lines per language, the audit holds whole repositories.
- **Node-centric tools** (impact, subgraph, neighbors, tests_for) resolve their node as above; they read `_nav_view(nodes, edges, scope, as_json)`, which is the resolved edge list under a scope that leaves nothing out by default; they order rows production-before-tests; and an empty result carries `_EMPTY_NOTE`. `_resolved` edges are never written back: `graphlore_prune` and `graphlore_validate`'s lint read the raw graph.
- **Analysis scope:** a tool that ranks or audits the graph takes `scope: str = ""` and goes through `_scope_view(nodes, edges, scope, as_json)`. Compute on `view.nodes` / `view.edges`, label with `_display_labels(all_nodes)`, put `view.payload()` under `"scope"` and wrap the text in `_with_note(text, view)` so what was left out is always stated. The default leaves out vendored/minified files and external nodes.
- **Path confinement:** the per-file analyzers and source hydration (spans, APIs, routes, `fetch`, `skeleton`, `prune`) resolve every path from the graph, a semantic chunk or a file/node argument through `spans._resolve_in_project`, usually via `_cached_file_analysis` or `_read_source_lines`. Don't open such paths directly. Three things sit outside it on purpose: `graphlore_build`'s `path` is unconfined by default (absolute and sibling-repo paths are a documented use) and is guarded only by the opt-in `_path_escapes_project` (`RESTRICT_PATHS`, forced on for HTTP transports); `graphlore_project` accepts any directory and is refused outright under `RESTRICT_PATHS`; and freshness/diff/watch read git-reported paths relative to `config.PROJECT_DIR`. `review._count_mentions` walks the project directory itself (like `_route_candidate_files`) and never follows a link out of it.
- **`server.py` re-exports private helpers** from the lower modules (`# noqa: F401`) because tests reach them as `server._x`. A new helper that tests use that way needs adding to the re-export block.
- **stdout is the protocol on stdio transport**; diagnostics (boot banner, warnings, watcher logs) go to stderr.
- **Naming:** `graphlore_*` tools and `GRAPHLORE_*` variables belong to this project. `graphify-out/`, `.graphify_labels.json` and the `graphify` binary are artifacts of the wrapped CLI and keep their names.

## When adding or changing a tool

A tool is registered with `@_tool(annotations=ToolAnnotations(...))` in `server.py`; keep it read-only unless it genuinely mutates state and set the matching hint. The change also touches:

- the tool list in the `server.py` module docstring, and `LEAN_TOOLS` / `LOCATE_TOOLS` if it belongs in a trimmed surface. `lean` is the default surface, so a tool outside it is invisible to most users unless they set `GRAPHLORE_TOOLSET=full` (the plugin does)
- `_instructions(active)` and the prompts (`_render_prompt` steps) if the tool belongs in the recommended flow: they name a tool only when it is registered. A reply that points to another tool wraps the pointer in `_tool_hint(name, text)`
- `test_tool_and_prompt_registration` in `tests/test_tools.py`, which asserts the exact tool count (33)
- the tool tables in `docs/tools.md`, the README's table of the 12 `lean` tools if the tool is in that set, and the "33" / "12" counts in both
- `.claude/skills/graphlore-explore/SKILL.md` (shipped to users by the plugin)
- `CHANGELOG.md` under `[Unreleased]` — every behavior change gets an entry there (Keep a Changelog format)

The version is duplicated in `pyproject.toml`, `server.__version__`, `.claude-plugin/plugin.json` and `server.json` (twice there; tests compare the last three), and recorded in `uv.lock`; run `uv lock` after a bump. The release steps, including the PyPI publish workflow, are under "Releasing" in `CONTRIBUTING.md`.

## Documentation layout

`README.md` is the landing page, and PyPI's long description: what graphlore is, quick start, the 12 `lean` tools, the benchmark headline and an FAQ. Keep it short; detail goes to `docs/`:

- `docs/tools.md` — all 33 tools, resources, prompts, what a result carries
- `docs/concepts.md` — resolved edges, import checks, analysis scope, freshness, the search bridge (built-in index or semble), naming communities
- `docs/configuration.md` — running, the plugin, toolsets, transports, the network table, environment variables
- `docs/benchmark.md` — method and results (`docs/benchmark*.html` are the rendered reports)
- `docs/benchmark-polyglot.md` — every tool run on 31 real repositories in 14 languages: what works per language, what does not, and the findings (`benchmarks/polyglot.py` reruns it), and the second set of 14 (`--set 2`), chosen to be unlike the first. `benchmarks/results-polyglot.json` is the first set's baseline
- `docs/resolution-rules.md` — the name-resolution rules of each language as a list (scopes, imports, member lookup, overloads, written types), where the language defines each, and whether the engine follows it; generated by `benchmarks/conformance.py --markdown` from the cases there
- `docs/native-engine.md` — the native engine: what it extracts, how it resolves edges, its communities and incremental updates, its comparison with graphify on the same 31 repositories (`benchmarks/compare_engines.py`, `benchmarks/polyglot.py --engine native`), and the roadmap to replacing graphify

Links from the README into the repository are absolute (`https://github.com/yasinyaman/graphlore/blob/master/...`) because relative links break on PyPI; links between the `docs/` files are relative. The README's first paragraph and its FAQ headings are written to be quoted by search engines and AI assistants: keep them plain, literal and true to the code.

## MCP Registry entry

`server.json` at the root is the manifest for the official MCP Registry (schema `2025-12-11`). Its `name` (`io.github.yasinyaman/graphlore`) must also appear as `mcp-name: ...` in `README.md`: the registry verifies PyPI ownership by finding that string in the package's README, so the HTML comment under the README title is load-bearing. ## Claude Code plugin

The repository root is itself a Claude Code plugin and its own marketplace (`.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json` with `"source": "./"`). Consequences:

- `.claude/skills/` is what the plugin ships to users, not only a project-local skill directory. Anything added there is installed for everyone.
- The plugin's MCP server runs `uvx --from "graphlore[graphify,treesitter,semble,embed] @ ${CLAUDE_PLUGIN_ROOT}" graphlore`, i.e. it builds this package from the installed copy of the repo. Renaming the console script, the package or those extras breaks the plugin.
- Users stay on the manifest's `version` until it changes, so a fix reaches plugin users only with a version bump.
- Check manifest changes with `claude plugin validate --strict .`; it passes clean.
- Claude Code's project instructions live in `.claude/CLAUDE.md`, not at the root. A `CLAUDE.md` at a plugin root is not loaded as plugin context and makes the validator warn, so don't add one there.

## The native engine (`engine/`)

- `src/generic.rs` is the port of `spans.py`'s definition rule (`_spans_treesitter` and its helpers), in the same order. Keep the two in step: `tests/test_engine.py` asserts that `graphlore_engine.file_spans` equals `spans._spans_treesitter` (and, for Python, `spans._spans_python`) on a snippet per language. A rule change in `spans.py` gets the same change in `generic.rs`.
- A language is a `Lang` variant, a row in `SPECS` (`src/lang/mod.rs`: name, extensions, grammar crate) and a module in `src/lang/` implementing `LanguageModule`, whose methods all default to the generic rule; a module overrides only what its grammar does differently: definitions (`kind_of`, `region_start`, `end_line`, `test_regions`, `refine`, `bound_functions`, `emits_node`, `extra_def` for properties / constants), and the facts resolution needs (`imports_of`, `heritage_of` / `heritage_owner`, `package_of`, `exports_of`, `object_of`, `refs_of`, `is_field`, `builtins`). Each new language gets a sample in `tests/grammars_load.rs`, goldens in `tests/spans_golden.rs` and a small project in `tests/edges_golden.rs`, and a resolver for its module paths in `src/resolve/modules.rs`.
- `src/refs.rs` reads the uses (calls, constructions, bases, types, decorators, attribute reads, values passed) and typed names (parameters, fields, `x = Foo()`) with field-name rules shared by the grammars; `src/resolve/` turns them into edges. Resolution order matters and is documented at the top of `resolve/mod.rs`: scope lookups are `EXTRACTED`, a project-wide guess by name alone is `INFERRED` and needs evidence (a unique candidate; for an unknown receiver, a distinctive method name in a file the caller imports or its directory). Never add a lookup that guesses before the scopes are exhausted, and an external module's contents name nothing.
- Locals in resolution (`resolve_path`): a typed local resolves through its type; a local the walk cannot type still hides every outer name of its own (only a distinctive method name is tried on it, `INFERRED`), except a bare call beside a typed local (`baseUrl(…)` beside `String baseUrl`), a local assigned from the outer thing of its own name (`let agent = agent();`) and an assignment hint (`Local::assigned`: `service = make()` where assigning declares nothing), which keep the outer meaning. PHP `$x` keeps its `$` in paths and is only ever a local. A use inside a field first assigned in a method belongs to the method (`refs::homes`), not to the class the field hangs off. A name bound to an import (`const x = require('m')`, `require('m').y`) is not a state definition. An `Extension` definition never answers a name lookup (`top_in`), and neither does an anonymous class (`Def::anonymous`: the method around constructs the type it implements, the class has it as its base). A closure's parameters are names of the closure only (`refs::bind_closure_params` renames their uses to `name@byte`); never record them as locals of the function. A closure no definition holds (`test('…', () => { … })`, an RSpec `it … do … end`, a module wrapped in a function) is a definition of its own (`Def::block`, `refs::add_blocks`): no node (`assemble`), no name (`index`), its parent the block around it, the home of the uses and locals inside it (their edges leave from the file), and the parent of a definition written in it, which it sees as a function sees its nested ones (`resolve_name_any`); an RSpec `let` keeps its own `scope_lines` and is never re-parented. A block is never a span: `file_spans` leaves it out (`tests/test_engine.py` holds a snippet with a callback at file level). A Rust macro outside any definition is a block too, and `refs::macro_refs` returns the locals its arguments bind (a closure's typed parameters, a `let` in its body) with the uses, `name@byte` moved to the file's bytes. A closure called where it is written as a declaration's value (`var X = (function () { function X() {} return X })()`) gives the definition of the declared name written in it `Def::returned_out`: `index` registers it in the scope of the declaration too (it stays the block's child, so it still sees the block's other definitions), and the declaration is no local. A declaration whose value is a function that is a definition of its name (`const f: T = () => …`) is no local either. `assigned_member` is a function assigned to a function as its member (`X.extract = function`), in its file. RSpec `shared_examples` and the places that include them are `FileFacts::shared_examples` / `example_includes`: `shared_example_let` answers a bare name in the examples with the `let` in scope where they are included, only when every including place gives the same one. An extension function or method (`Def::receiver`) is a member to its callers (`extension_method`: `EXTRACTED` on a matching receiver type, `INFERRED` on a single visible candidate). The receiver's type counts with its bases (`extension_for`), a field or property of a type the project does not define with the type it declares (`extension_on_member`; `refs::predefined` keeps C# `string`), a local with the type its value constructs (`local_built_type`), and never by a `CSHARP_CORE_METHODS` name on a receiver that is no project type. A C# 14 `extension(T x) { … }` block parses as a constructor named `extension` with local functions: `CSharp::receiver_of` gives them the block's parameter type, and `fit` takes no receiver off their parameters (`in_extension_block`). A C# partial type is all the definitions of its fully qualified name with as many type parameters (`partials`): `members`, `field_of` and `bases` read them all. A construction also calls the constructor the type declares, picked among overloads by argument count (`RefFact::args` / `Def::params`) and left out when that does not decide. Ruby: a bare name that is no local is a call, a module is every file that opens it (`reopened_member`, `qual_key`; `reopened_base_member` for what another opening mixes in or extends, and `Ruby::heritage_of` reads the block of `X = Struct.new(…) do … end` too), a top-level method of a file the caller does not require is not in scope, and a name called without parentheses is followed through what it returns. An RSpec `let(:x) { … }` / `subject` is an extra callable definition (`Ruby::extra_def`) with `Def::scope_lines`, the `describe` / `context` block it is written in: only the scoped lookup at the top of `resolve_name_any` finds it (the innermost block around the use), never `top_in`, `by_qual` or a guess by name; its result is the block's last expression (`Def::returns`), and the call that declares it is no use. `FileFacts::spec_includes` (`config.include M`) answers, in a test file only, a bare name nothing else does (`spec_helper_member`). What a call gives is `return_type`: the declared result, else what the body's `return`s and expression body construct when they agree (`Def::returns`, `INFERRED`; a closure's `return` is not the function's). A local keeps the whole chain it is assigned (`value_type` drops only a chain that starts at something unnameable), and inside its own initializer its name is the outer one (`own_initializer`). A Kotlin lambda with a receiver is a `ReceiverScope` (`x.apply { … }`, `with(x)`, a parameter typed `T.() -> R` via `Def::lambda_receiver`); `RefFact::recv` names the innermost one around a use, and `receiver_member` is asked after the locals and before the class around — never while typing a path written elsewhere (`type_of_path` clears it). An untyped local or parameter is an unknown receiver (`unknown_receiver`); in Ruby and Swift only for a name no other type answers to (`sole_holder`: no property, no `FileFacts::attrs` entry, not a core-library name), and never on a local of an external type, which only an extension can answer. Overloads (`Family::overloads`: Jvm, C#, Swift, C/C++) are chosen after resolution by `pick_overload` / `fit`: `Def::plist` (names, written types, defaults, varargs) against `RefFact::args` / `hints` (literal kind, typed path, label); `fit` returns `None` only when the facts rule a candidate out, and what they do not say counts for nothing — never make an unknown a mismatch. Constructors go through the same `fit`, with a Kotlin class's primary constructor (the class's own `plist`) as a candidate that names no definition. A result typed by a self-bound type parameter (`Def::self_params`) is the type the method was called on; a local's `given` type (one type argument or class literal of its value's call) is its type only through `given_result`'s checks. When several overloads fit alike `pick_overload` returns them all and each edge is `INFERRED`: never name the first as if it were known. A local with no type is typed by `structural_type` (the one type answering every non-core member used on it, two names at least); a collection's element type is `Local::elem` / `ParamFact::elem` / `Def::elem`, a path ending in `refs::ELEMENT` (`[]`) names an element (`elem_of`), and loop variables, iteration-lambda parameters and `xs[0]` are locals with such a path. The path walk (`resolve_path_inner`) carries `many`: what it holds is a collection of itself, after a name, field or call declared as one when something of collections follows (`is_collection_step`), after a `KEEPING_METHODS` name, or after `refs::MANY` (`[+]`, which `refs::mapped` ends a mapping's path with: `xs.map { it.owner }` is `xs`, `[]`, `owner`, `[+]`); an `ELEMENT_ACCESSORS` name or `[]` leaves it, `UNWRAPPERS` are skipped on the element just taken, and a path that ends `many` names nothing unless `elem_of` asked (`want_many`). A collection method as the last name of a call is the library's: never an edge to the element type. A path with `[]` / `[+]` that does not resolve is retried as an unnamed receiver (`()` and what follows). It also carries `sealed`: `t` is what a closed wrapper holds (`Def::sealed` / `Local::sealed`, read by `refs::sealed_type` from the `SEALED` names; `Def::wraps` is what a wrapped result or field holds, and `return_type` reads it first). `refs::OPENED` (`[?]`, written by `path_of` / `value_type` after `await` and Rust `?`) and an `UNWRAPPERS` name open it, `SEALED_KEEPING` names keep it, anything else on a closed wrapper names nothing; `resolve_path_inner` takes `[?]` out of the path and keeps where it was (`opened_after`). `Result` and `Task` are wrappers only in Rust and C# (`refs::language_wrapper`): another project may define its own. Maps: `refs::map_value` gives a map type's values as its element and `keyed` (on `Def`, `Local`, `ParamFact`) says it is a map; the walk carries `keyed` and `indexed` (after a `PAIRING_METHODS` name) beside `many`. Three markers end a path to one of a collection: `[]` (`refs::ELEMENT`: an index or key, a map's value), `[*]` (`ITERATED`: what an iteration gives, nothing of a map or of pairs) and `[v]` (`VALUE`: the second of a pair taken apart, a map's value or the element beside an index); `elem_of_as` takes the marker. `KEY_LOOKUPS` give a map's value, `MAP_VIEWS` change what it is (`keys` gives the key type, `Def::key` / `Local::key` / `ParamFact::key` from `refs::map_key`, carried as the walk's `keys`). A fourth marker, `[k]` (`refs::KEY`), is the first of a pair taken apart: a map's key, a list's element, nothing beside an index; `[+=]` (`MANY_KEYED`) ends an `associateWith` mapping. `partition` taken apart keeps the collection for `[#0]` / `[#1]` (`partitioned`), `refs::zipped` gives each name of a pair over `zip` its own side, `refs::fold_value` is what a fold starts from (its result and accumulator), and `Def::returned_parts` (`note_parts`) names what a tuple part is when its type does not (`local_function`). The library-method rule (a collection's or wrapper's method as the last name of a call names nothing) holds for a call being linked, not for a local's value being typed (`linking_call`, `typing_value`). Generics: a class-like `Def::type_params` holds its own type parameters, and `targs` (on `Def` for a field's type and a callable's result, on `Local`) the type arguments written; the walk carries `Binds` (the generic type and what each parameter stands for, each with the file and scope it is written in), set from a local's or field's `targs` and passed through a result written with the class's own parameter (`binds_for`), and read by `bound_type` / `bound_field` only for a member of that very class and never for a method's own type parameter. A `BoundArg` carries the argument's element when it is a collection (`Def::targ_elems` / `Local::targ_elems`: `bound_param` answers whether the type is that element); a member a base declares takes the bindings the base is written with (`Def::base_targs`, `inherited_binds`, three levels); a local typed by its value takes the bindings its value's walk ends with (`end_binds`, `local_value_binds`, cached like `local_types`). The walk's `nest` counts lists of lists beyond `many` (`NESTING_METHODS`, `GROUPING_METHODS` add one, an element marker or `FLATTENING_METHODS` take one off); `ASSOCIATING_METHODS` make a map of the elements, `REDUCING_METHODS` give one. A mapping's function is read by `refs::lambda_result` (one expression, the tail where the language makes it the value, agreeing `return`s), `lambda_local` (a local of the lambda is its value) and `referenced` (`Item::owner`, `\.owner`); `rename_closure_heads` gives a local's path head, and a nested closure parameter's, the closure's `name@byte`. Tuples: `Def::rets` holds the parts of a tuple result (`refs::return_tuple`), `refs::destructured` finds a declaration that takes one apart and gives each name the value's path with `[#i]` (`tuple_part` / `tuple_index`); the walk turns `[#i]` after a callable into that part, and after a Rust tuple struct (`Def::rets` / `part_sealed` on the struct) into that field; `refs::member_path` writes a numbered member (`self.0`, Swift `both.1`) as `[#i]`, and `tuple_local_path` re-walks `p.0` / `p.Item2` / `p.second` of a local holding a tuple through the local's value; `return_type` names nothing for a tuple result outside Go. A parameter's `sealed` / `keyed` / `targs` come from its own node (`refs::param_node`). A base that resolves to the class itself is its namesake (`namesake`: `RestResponse<T> : RestResponse`). Swift's implicit members (`.status(301)`): `refs::implicit_member_call` writes the path `[refs::IMPLICIT, name]` with `RefFact::implicit` (`Implicit::Arg` — the call it is an argument of, as that call's index among the file's references —, `Typed`, `Return`), and `Project::implicit_member` looks the name up as a static member of the type that place gives (`call_target` resolves the enclosing call with its overload picked, memoized; the walk's per-reference state is taken out and put back with `suspend` / `restore`). The argument is `Arg::Implicit` to `fit`: a type with such a member fits, one without does not, a protocol says nothing. `overloads` of a Swift method include the members an extension of its type adds. A Rust macro's arguments are tokens to the grammar: `refs::macro_refs` parses the `( … )` / `[ … ]` token tree again as an expression (its own parse, so an error stays inside it and such a macro is skipped), runs the reader on it and places the calls at their bytes and lines in the file; only the first argument of `matches!` is read. CommonJS: a module used as a value is what it assigns to `module.exports` (`module_default`, asked by `resolve_path` only for a call, a construction or a type, and by `member` after the module's own names); `module.exports = require('./x')` is an `ImportForm::ReExport`, and `exports.name = bound` an entry of `FileFacts::exports`. `Scope::imported` also holds the files an imported module passes on (`passes_on`, three steps): every "in sight" rule reads it. A guess by a method's name (`fallback_method`) takes a function assigned to an object (`Def::object`, not `exports`) as a method, never a name in `ECMA_CORE_METHODS`, and is also asked for a module variable holding a project value the walk cannot type (`holds_project_value`; never a library's). The words for the object and its base are per language (`refs::receiver_word`, by `parse::current()`, the language of the tree the thread parsed last — several grammars report no name): `parent` only in PHP, `base` only in C# (its node kind `base` is a `SUPER_KINDS` entry), `cls` only in Python; `self` is the object everywhere. A resolution made by a name alone sets `Project::guessed` (`fallback_method`, the single-candidate arm of `extension_method`), and such a guess from a definition to itself is dropped in the main loop — never one a typed path, `self` or an overload tie made. Swift implicit members (`implicit_member`) also take a property's initializing closure (`Implicit::Return` up to a state def), a memberwise initializer's label (a struct with no `init`: the stored property), a library type's static member a project extension adds (`extended_type`), and `extension_property_hop` (a property extensions add to library types, one held type for every such property of the name). An enum case is a value of its enum (`type_of_path_inner`). `lombok_field` turns `getX` / `isX` / `setX` on a `@Data` / `@Value` / `@Getter` / `@Setter` type into the field, and the main loop writes `reads` / `writes` for such a call. `authenticatable_model` is Laravel's `auth()->user()`. `held_by_pattern` makes a binding it cannot type an untyped local; `ImportFact::public` is Rust `pub use`, passed on only through a star import (`rust_public`). `fallback_method` refuses `ECMA_CORE_METHODS`, `RUST_CORE_METHODS` and `CPP_CORE_METHODS` names, and `arg_fits` drops a primitive reading of a parameter type the project defines. A cast is a declared value type (`refs::is_cast`, `value_type`). C and C++ `Foo x;` is a local (the declarator is a bare `identifier`); C++ `Pool pool(context);` whose every "parameter type" is a bare name the function already has as a local or parameter is a variable (`refs::misread_variable`: a `New` ref, the arguments, a local), and the function declaration the grammar made of it keeps its span but is `Def::misread`: no node (`assemble`), no name (`index`), home to nothing (`homes`). A Swift stored property's type is its `type_annotation` child, which has no field name. `Random rnd(seed());`, a call where a parameter's type would be, is misread too, with the call as a use; `spans.py`'s grammar reads that one as the variable it is, so it is `Def::unspanned` and `file_spans` leaves it out. A C/C++ namespace's member is looked up in every block that opens it (`namespace_members`: its own block first, then each `Namespace` of the qualname, never a method defined there for a type); in the walk, the last name of a path takes the callable of that name and a name with `::` after it the type or namespace. C++ `using X = T<…>;` is a `TypeAlias` span definition (`alias_declaration` is named exactly: `generic::SYMBOL_TYPES`, `spans._TS_SYMBOL_TYPES`), and the walk fills its and a `typedef`'s `declared_type` and `alias_args`; `type_of_path_inner` follows a C-family alias to its type and `specialization_for` picks the specialization its `Def::alias_args` fit. A specialization (`Name<T, true>`) is indexed under its template's name too (`specialized`); a walk whose type came from the bare name is `unpicked`: `INFERRED`, a member only one specialization answers to is that one's, a name several declare none. A deduction guide is `Def::misread`. A C-family alias with one class-like child (`typedef struct X { … } X;`) is that struct (`type_of_path_inner`); its `declared_type` is a struct specifier's name, never what the body holds. `refs::declarator_params` follows the declarator chain to a C function's parameters. C `extern T x;` is a `decl_only` state definition (no node: `assemble`), mapped to the definition by `best`; `CFamily::state_defs` sees a file-level declaration through `#if` groups and `extern "C"` blocks, never one without its own `;`. A function put in a slot of a struct (`FileFacts::slots`, read by `refs::slot_facts` from an initializer, by name or position, and from `x.f = func;`) is a `dispatches_to` edge from the slot (`Project::slot_of`: by name, or the struct's fields in source order, data fields counted) to the function; only a bare name of a project callable. A field of an anonymous struct type has `Def::inline_body`, and `members` answers for it with the outer struct's children inside that body. JS `this` in a function expression no definition holds carries `RefFact::this_of` (what the function is attached to: `obj[x] = function`, or the call it is passed to): `this_of_member` reads it (`EXTRACTED` for `obj[x]`, `INFERRED` for a Mongoose schema's callback, the file's `methods`); `constructor_member` is an ES5 constructor's prototype; `handed_member` types an untyped `req` / `res` by the project's own `Object.create(http.IncomingMessage.prototype)` object (`Def::created_from`) and a local constructing a `mongoose.model('X')` (`Def::model_name`, `FileFacts::models`) by its schema's `methods`, both `INFERRED`. An object literal assigned to a member gives its functions that member as `Def::object`. `FileFacts::callbacks` (a function passed to a call: its first byte, the call's path, its parameters) types the second parameter of a callback a Mongoose model's static is handed. `explain_unresolved`'s marks for rows that are no gap read `FileFacts::runtime_props` and `request_props` / `request_aliases`; `vendored_path` is the analysis scope's path rule. C and C++ sources are parsed with an `#if` whose every branch leaves the same number of braces open blanked to its first branch (`parse::blank_duplicate_branches`, `spans._blank_duplicate_branches`: the same rule, kept in step like the span rule); a C# source with an `#if` that opens in the middle of an expression (the code line before it ends no statement, block, attribute or list item) keeps its first branch and loses the directive lines and the other branches (`parse::blank_expression_branches`, `spans._blank_expression_branches`, in step likewise). A C# namespace written as a block sees the namespaces around it (`modules::scope_lookup`) and is every block that opens it (`namespace_members`, as in C and C++). Kotlin's grammar drops some comments from the tree: `Kotlin::region_start_in` reads the comment lines above a definition from the source, only where the tree has no comment node (one it has and did not attach is the first comment of a block, no part of the region). A call the walk could not follow is asked last for the one extension in sight written for a type the project does not define (`library_extension_call`, `INFERRED`): never for a local whose type the source names, a receiver the walk gives a project type, a name that is also a member of a project type, a static call on a library's type, or from the extension to itself. C# primary constructor parameters (a `parameter_list` on the class) are field locals like Kotlin's. `const { a, b: c } = f()` gives locals with the path `f`, `()`, key; `Def::returned_members` (`note_members`) is the object literal a function returns, and the walk turns `()` + key into the function the member names (`local_function` resolves such a local when it is called). A Python `@property` (`is_property`) read with more after it is its `return_type`. A C# path whose lowercase head names nothing in sight, called by an extension's name, goes to `extension_method` with no receiver type (top-level programs). `RefFact::targs` counts the type arguments a call writes (C# `generic_name`, Java `type_arguments`): `fit` rules out a callable of another number of `Def::type_params` (`writes_type_arguments`: C# and Java only), and `pick_overload` prefers the plain callable over a generic twin whose parameters are written the same (`ParamFact::written`, type arguments and all) when the call writes none. A state definition is typed by the type its declaration writes (`declared_state_type`) before the value it is assigned (`state_type`). A call in the middle of a path has no arguments in the facts: `overload_giving` follows the one overload whose result has the member asked next (`INFERRED`). A head that resolves to a callable with a member asked of it, not called, gives way to a typed field of that name (`resolve_path_inner`), and so does a member: read without a call, with more after it, it is the field beside a method of its name (never in Ruby), and `qualified` tries every namespace around a C# file's own. Names a statement binds with a type the source states are locals (`refs::bound_by_pattern`: a typed loop variable, Java / C# type patterns, Rust `if let` / `while let` / `match` arms through `held_by_pattern`, Swift `if let` / `guard let`): the path is the declared type, or the value's path with `[?]`; a binding that only shadows its own name makes no local. `type_of_path_inner` types a value that ends on a field or variable by `held_type`. `refs::path_of` reads the callee of a call once and hands it to `mapped_call` — reading it twice doubles the work at every link of a chain. `closure_params` returns parameters in the order written (`_` keeps its place): which one is the element depends on it (`ITERATION_METHODS` the first, `INDEXED_METHODS` the second). `local_type` guards against coming back to the local it is typing (`typing`); anything that resolves a path while typing one goes through it or through `type_of_path`'s depth guard, or the build can recurse without end. Rules the checklist added (`benchmarks/conformance.py`, engine 0.5.46), each with a case there and a golden at the end of `tests/edges_golden.rs`: a cast used where it is written is the path of its type and `()` (`refs::is_cast` in `path_of`: Java / C# casts, `as`, Swift `as!` in a one-value `tuple_expression`, Go `type_assertion_expression`); C# `a?.b` is a `conditional_access_expression` whose `member_binding_expression` is put after the object (`refs::BOUND`); a binding opened out of a declared local (`[opt, "[?]"]`, or `[r]` for the `it` of `r.let { … }`) is typed with `calling` off (`holds_declared_local`), and what an optional gives once opened is no collection of it (`elem_of_as`). A member asked of an `EnumMember` is the enum's, after what the value declares itself (`member`). A Kotlin / Swift `typealias` of one named type has `declared_type` and `type_of_path_inner` follows it as it does a C alias; C++ `namespace u = util;` is `FileFacts::ns_aliases`, read at the top of `resolve_path_inner`. `value_node` finds a Kotlin property's value after its `=` and the first of a Go `expression_list`; a Ruby constant assigned a constant has it as `value_path`; a Scala `val` / `var` not directly in a class or object body is a local (`locals_of`), not a definition. Ruby `@x` is the path `self`, `x`, and `@x.m` on a field the walk cannot type is an unknown receiver (`resolve_path`'s fallbacks). `callable_reference` is no call kind: it and `method_reference` are `Indirect` refs wherever they are written (`refs::referenced`), `Foo::class` (Kotlin, in both shapes its grammar gives it; PHP) a `Type` ref with the context `class_literal`, PHP `[$this, 'm']` an `Indirect` (`refs::php_callable`), PHP `static` the class around (`new static()` resolves through the `self` arm only for a `New` ref). A Scala attribute read that resolves to a callable taking nothing is `calls`. Order: `Local::byte` and `RefFact::byte` are in the facts cache (they were `serde(skip)`: never read a position that is not). A use before the first declaration of a local keeps the outer name where a declaration makes the local (`local_keeps_outer`: not Python, Ruby, PHP). Rust keeps every non-field local of a name (`refs.rs`'s dedup), a `let`'s `byte` is its end, and `Project::shadows` / `local_in_force` pick the last declared before the use (the first of those at one position: the arms of a `match`); typing a redeclaration's own value names the declaration before it (`declared_before`), and one the walk cannot type gives way to an earlier typed one, `INFERRED`. `Project::locals` names the first of several, as before. A C / C++ declared variable that is no project class hides a function of its name. C++ types: `qualified_identifier` with a namespace or type scope and a plain type name is one type path (`types_in`; one with template arguments is still read through its parts); where a type is written (`naming_type`: `types_only`, or a `Type` / `New` / base ref, `Project::ref_kind`) a name before `::` is never the variable of that name, a qualified path that does not resolve is retried by its last name, and of several definitions of one qualified name the asking file's own come first, then those of files it includes (`Project::asking`, in `member` for a namespace and in `qualified`). A scoped path that resolves to a class is a `references` edge in C / C++ (never to an enumerator). `refs::RUST_WRAPPERS` (`Box`, `Arc`, `Rc`, `Cell`, `RefCell`, `Pin`, `Cow`) are wrappers only in a Rust tree. Rust `self::f` is the path `f`; `super` inside an inline `mod` is the module around the block. - Edges: one per `(source, target, relation)`, both ends real nodes (external names get `type: "external"` nodes), `source_file` / `source_location` of the site, `confidence` and `context`; import edges carry `runs` (`module-level` / `deferred` / `type-checking`), which `ImportChecker.kind` takes as given. A graph whose `graph` header says `engine: graphlore` and `schema_version` ≥ 2 is marked by `graph._engine_resolved(nodes)`, and `resolve._resolved` adds nothing to it.
- `src/community/` detects communities on the assembled graph (`leiden.rs` is the algorithm, `mod.rs` the weights, graphify's split rules, names, id remapping and saved-name pruning). It must stay deterministic and stable: nodes are visited by a hash of their id, never a global shuffle; a build starts from the previous graph's communities (`Previous::read`, the graph.json it replaces) and settles until a pass returns its own start. `tests/incremental.rs` asserts that an update and a full build from the same previous graph write the same graph.json; keep that true when touching either. The weights are measured (`compare_engines.py --communities`, see `docs/native-engine.md`); change them with numbers.
- `src/state.rs` records reads and writes of names and members during the fact walk (assignment, `+=`, `x[k] = v`, `del`, `++`, a mutating method on a collection); `src/resources.rs` the uses of environment variables, files, SQL tables, events and cache keys by a literal key, per language in tables, and the table a data model declares (`Def::table`). Each language declares its state in `LanguageModule::state_defs` (module variables, constants, fields), `assignment_declares` (Python, Ruby: `x = 1` is a local) and `needs_import`. Rules that keep it honest, each with a golden in `tests/state_golden.rs` / `tests/resources_golden.rs`: a local hides a variable of its name (but `local.field` is the object's field); a mutating method counts only on a container (`Def::container`) and is `INFERRED`; a constructor setting its own fields couples nothing; a resource is a node only when two definitions touch it, an event only when the project both emits and listens, and never for a generic stream / DOM event name. The walk passes its stack of ancestors to these (`anc`): tree-sitter's `parent()` walks down from the root again, so never climb with it in a per-node visitor.
- `src/http/` reads routes and requests per language (`python.rs`, `ecma.rs`, `jvm.rs` for Java and Kotlin, `csharp.rs`, `go.rs`, `rust.rs`, `ruby.rs`, `php.rs`), after `src/graphlore/routes.py`'s rules and gates (a framework is read only in a file that imports it, by name or, in the framework's own repository, by a relative path to the directory whose `package.json` names it): `RouteFact`s, routers with a prefix (`RouterFact`, `scope` for one bound in a definition), mounts (`MountFact`: a router named, a module required, a function's router parameter `Mounted::Param`), global or per-file prefixes (`GlobalPrefix`) and requests (`CallFact`). A route's router path can be `SELF_ROUTER` (the router the enclosing function builds) or `[PARAM_ROUTER, "N"]` (its `N`th parameter). `src/resolve/http.rs` composes the full paths across files (`compose`, memoized, depth 8), turns them into route nodes (unique ids: two paths that slug alike get a counter) with `handles` edges, and links requests to routes (`link_calls`): only production code (requests in test code are counted), segment by segment, the most literal match first, then the route nearest the request; `EXTRACTED` only for a single candidate with a known method and no value-against-parameter segment. A handler path is taken only from an `EXTRACTED` resolution; `Handler::Class` finds a controller by name (`articles#index`, `UserController@store`). Keep `routes.py` and these readers in step: `route_parity.py`-style checks (every `routes.py` row of the audit repositories is a route of the native graph) and `tests/http_golden.rs` hold them.
- The reader and the resolver are shared by the 14 languages, so **a rule that is one language's asks which language it is reading** (`parse::current()`, `Family`, `FileFacts::lang`): a name table consulted without asking has made `Box` a wrapper in Java and dropped the `$` of a TypeScript name. `benchmarks/neutrality.py` checks it by differential testing: every name of every `const NAME: &[&str]` table of `refs.rs`, `resolve/mod.rs`, `state.rs` and the language modules, plus name shapes and other languages' keywords, as a method on a typed receiver, a method called on `self`, a bare function and a generic type the project defines itself, in each language, against the same project with a neutral name. A new table or a new spelling rule is run through it (`--tables NAME`), and a row it adds to `benchmarks/results-neutrality.json` is a leak unless the language reserves the name. A wrapper's name is the project's own type in a file that sees the project define it: the reader cannot know, so `lib::reread_shadowed` reads those files a second time with the names in `parse::shadowed` (it is the same from the cache: what a file defines and imports does not depend on it). `self` / `super` are plain names where the language has no such word and the scope has one (`plain_word` in `resolve_path_inner`).
- `src/walk.rs` honours `.gitignore` for what git does not track, and reads what it does: `tracked_but_ignored` asks `git ls-files` (the engine's one subprocess; no git or no repository adds nothing) for the tracked files the walk left out, minus hidden paths, `SKIP_DIRS`, the output directory and the root's `.graphloreignore` / `.graphifyignore`. A manifest found that way counts (`packages/zod/package.json` under `**/package.json`). `tests/tracked.rs` holds it.
- Where a language's compiler says what a name is bound to, it is the judge: `benchmarks/oracle_typescript.py` compares the engine's edges with the `.symbols` baselines of the TypeScript compiler's test suite, `benchmarks/oracle_scala.py` with the Scala 3 compiler's SemanticDB expect files, `oracle_kotlin.py` with the Kotlin Analysis API's resolver tests and `oracle_swift.py` with the Swift index tests; `oracle_go.py`, `oracle_rust.py` and `oracle_csharp.py` ask `go/types`, rust-analyzer and Roslyn about whole repositories (precision: an edge whose site the compiler has an answer for goes to that declaration; the "missed" list is a list to read, not a recall). Run it after a change to the shared resolver, read the `wrong` rows, and turn a real one into a conformance case first. `benchmarks/verify_cases.py` checks that the checklist's own programs are ones their languages accept.
- A rule of a language is a case before it is code: `benchmarks/conformance.py` holds one small project per name-resolution rule (the edge the rule says is there, the edge that must not be), and `benchmarks/results-conformance.json` their state. A resolution change runs it with `--baseline` (a case it breaks exits 1), a rule found missing on a repository is added there as a case first, and `docs/resolution-rules.md` is regenerated from it. A failing case is an open defect, not a failing test: the goldens in `engine/tests/` hold what works.
- An edge only graphify has is a gap only when it is right: for a Go, Rust or C# repository `benchmarks/verify_graphify.py` asks the compiler about each of graphify's edges and gives the share of the confirmed ones the native graph has; read that number, and its list of confirmed edges the native graph lacks, before chasing a row of `compare_engines.py`. The confirmed edges are a floor: `--baseline benchmarks/results-verify-graphify.json` fails a build that lacks more of them, per repository and kind, than the file says (`--update` after closing some). What the resolver leaves out is measured, not guessed: `BuildOptions::unresolved` (`build --unresolved PATH`) writes each call with no edge whose name is the one callable of that name in the project, with the reason (`Project::explain_unresolved`), and `benchmarks/unresolved.py` counts them. Run it before and after a resolution change (`--json`, `--baseline`) and read samples of the reason the change is for; asking for the rows must never change graph.json (`tests/unresolved.rs`). A row carries `library_like` (why it is most likely a library's name: a core name — the `*_CORE_METHODS` tables, Rust's and C++'s only for this —, a library's receiver, a capital head that names nothing of the project, `self` under an outside base, a test-code definition for a production call) or null; mark a new kind of noise there, not in the script. A member of a type that implements a library type (`implements_library_type`: an outside base not in `MARKER_BASES`, never Ruby) is marked on an untyped receiver (`UNTYPED_RECEIVER_REASONS`), not when the receiver's type is known. A path that reaches something written with a library's type (`library_typed`, `is_outside_local`) is the library's unless the one definition is an extension; a bare call names no method where `Family::implicit_this` is false; an RSpec `let` is a candidate only for a bare name; a member of a name a type declares with no `def` (`self.attrs`: a Ruby `Struct` member, `attr_accessor`, `def_delegators`) is marked whatever the receiver.
- `src/cache.rs` is the facts cache behind `update=True` (`BuildOptions.incremental`): bincode, keyed on engine version, schema and build options, read with a size limit so a damaged file cannot ask for memory. A new field on `FileFacts` and its parts must deserialize (`Deserialize`; a `&'static str` goes through the `Context`-style alias and `cache::static_str`).
- Grammar crates must depend only on `tree-sitter-language` (not on the core crate), or they pin a second core. Kotlin is `tree-sitter-kotlin-sg` (the fwcd grammar `spans.py`'s rules assume) because `tree-sitter-kotlin` pins an old core.
- graph.json keeps graphify's shape and conventions so every reader works unchanged: node-link top level, path-slug ids (`core/src/lib.rs` + `Fixed.acquire` → `core_src_lib_fixed_acquire`), labels `name()` / `.name()` / bare, a file hub per file, `source_location` whose leading number is the definition line. Additions are extra keys (`kind`, `qualname`, `language`, `region_start`, `end_line`, `test`, edges' `runs`, externals' `ecosystem`, top-level `graph.engine` / `graph.resolution` / `graph.communities`, nodes' `kind: variable | property | constant`, resource nodes' `type: resource` / `resource` / `key`); `community` / `community_name` are graphify's own keys; never write `type` or `line` on code nodes, which the accessors prefer.
- The engine's version lives only in `engine/Cargo.toml` and is independent of graphlore's. `SCHEMA_VERSION` (`src/lib.rs`) changes when graph.json changes in a way readers must know about; `engine.SUPPORTED_SCHEMAS` lists the ones this graphlore reads, and `test_engine_version_pins_stay_in_sync` checks the two.
- No `engine` extra in `pyproject.toml` until `graphlore-engine` is on PyPI: `uv lock` resolves every extra and would fail.

## Tests

Everything is in `tests/test_tools.py`, except the native engine's end-to-end tests, which are in `tests/test_engine.py` and skip themselves when `graphlore_engine` is not installed; its Rust tests are in `engine/tests/`. An autouse fixture clears `GRAPHLORE_ENGINE` for every test. `tests/conftest.py` pins `server.TOOLSET = "full"` for every test: `server.main()` trims the shared `server.mcp` for real, and the default is `lean`. Tests call tool functions directly (`server.graphlore_overview(as_json=True)`) and parse the result. The `project` fixture gives a temp project with the 5-node fixture graph; `empty_project` has no graph. Tests needing a specific shape write their own `graphify-out/graph.json` into `tmp_path` and repoint `PROJECT_DIR`. Protocol-level behavior (schemas, sampling) uses the SDK's in-memory `Client(server.mcp)` driven by `asyncio.run`; there is no pytest-asyncio. Freshness/diff tests build a real git repo in `tmp_path`.
